# 课程文档编写规范

`docs/` 下的编号文档是一套面向零基础学习者的 Spring Boot 教程，按顺序阅读。新增或修改文档时遵守下面的约定。

## 技术基线

- Spring Boot 2.7.18，Java 8，Maven，macOS 终端，`curl` 验证接口。
- JPA 相关的包名是 `javax.persistence`、`javax.validation`，不是 `jakarta.*`。
- 不要把 Spring Boot 3 的写法写进文档。

## 每篇文档的固定结构

1. `# 第 N 步：标题`
2. `## 这一节要完成什么`：说明上一节留下的问题和本节的目标。
3. `## 1. ...` 起的编号小节：按操作顺序写，包含 IDEA 中的具体操作步骤。
4. 每个新增的类、方法、注解、配置项都要单独解释作用。
5. 验证小节：给出可复制的 `curl` 命令和预期输出。
6. **`## N. 完整调用链路`：必须是正文的最后一个编号小节**，见下一节要求。
7. `## 成功标准`：可自查的清单。
8. `## 常见问题`：报错信息和对应的检查方法。

## 新增代码的说明要求

每新增一个类、接口、注解或配置项，文档必须交代清楚四件事，缺一不可：

1. **作用**：一句话说明它解决什么问题。
2. **编译期引用**：谁引用它，它又引用了谁，写明引用方向。跨包引用时说明 import 的来源，同包不需要 import 时也要点明原因。
3. **对象从哪来**：是 Spring 注入的，还是代码里 `new` 出来的，并说明判断依据（干活的对象交给容器，装数据的对象每次新建）。
4. **运行期触发**：谁在什么时机调用它的方法。
5. **去掉会怎样**：删掉这个类或这个注解，程序会出现什么现象。

其中第 3 点最容易漏。项目里有一类代码没有任何业务代码调用它，全靠框架回调，例如实现了 `CommandLineRunner` 的类、`@RestControllerAdvice`、`@Configuration`、`@Scheduled` 方法、AOP 切面、事件监听器。写到这类代码时必须显式声明：

- 项目中没有任何一行代码调用它。
- 由哪个组件回调，发生在启动阶段还是请求阶段。
- 触发它的具体条件是什么。

否则读者会把它当成没人用的死代码。

同时要区分“被引用”和“被调用”。一个类可能只被一个地方引用（例如响应模型只出现在处理器的返回类型上），但这不等于它没用。文档要把这两件事分开说明。

还要区分“创建对象”和“调用方法”。有些类由我们创建、由框架调用它的方法，例如响应模型由处理器 `new` 出来，getter 由 JSON 序列化组件调用。这两个动作的发起者不同，要分别写清楚。

调用关系是这套文档的主线。宁可多写一段引用与调用说明，也不要只给出代码让读者自己猜类之间怎么串起来。

新增分支逻辑（异常处理、条件返回、拦截判断）时，除了命中分支，还要说明没有命中时的兜底路径由谁负责。

## 完整调用链路小节的要求

每篇文档结尾都要有这个小节，帮助读者把本节新增的内容放回整条链路里理解。要求：

- 用 ```text 代码块画链路，节点之间用 `↓` 连接。
- 必须包含一张“本节新增类的引用与调用关系”表，四列：类名、谁引用它、运行期谁调用它、触发时机。
- 区分启动阶段（每次运行应用一次）和请求阶段（每个 HTTP 请求一次），不要混在一张图里。
- 链路要包含本节新增的环节，并标出它插入在哪一步之后。
- 给出一张“每一层负责什么”的表格，或说明与上一节链路的差异。
- 尽量附上真实控制台日志或响应片段，并注明它对应链路的哪一步。
- 同一篇文档里不要画多张覆盖同一段链路的图。需要在前文提到时，用“见本节第 N 步”指向这个小节。

## 不要把内部口径写给读者

这份规范本身以及编写过程中的约定，属于内部内容，不写进文档站的任何页面。

- 首页、目录页、章节开头只介绍内容和目标：这一节要解决什么问题、涉及哪些技术、完成后能得到什么。
- 不要出现“本教程要求每节都……”“每一节都会说明引用关系和调用链路”这类描述写作流程的句子。约定应该体现在内容里，不需要向读者宣布。
- 不写读者的水平判断，也不记录提问过程或修订原因。需要说明历史差异时，只客观描述行为变化，例如“上一节返回 204，本节改为 404”。
- 首页与目录的介绍以事实为主：技术栈版本、覆盖范围、阅读顺序、前置条件。

## 按零基础讲解 Java 语法

读者可能是刚开始学 Java 的人。除了框架用法，代码里出现的 Java 语法本身也要解释。

- 每个语法点在**第一次出现的那一篇**解释清楚，后续篇目只用一句话回指，例如“原因和第 6 篇讲过的一样”。
- 需要解释的典型语法：数字字面量后缀（`1L`、`1.5f`）、基本类型与包装类的区别、`null` 的含义、泛型写法、`Optional`、lambda 与方法引用、可变参数、静态导入、接口与实现类、继承与重写、异常的受检与非受检。
- 解释顺序固定为三步：这个写法是什么意思、为什么这里必须这样写、写错会看到什么报错。
- 报错信息尽量给真实的编译器或运行时输出，并说明如何自己复现。
- 遇到两个容易看混的写法要并排对比，例如 `Long` 与 `long`、`@Mock` 与 `@MockBean`、`orElse` 与 `orElseThrow`。

## 写作风格

- 使用简体中文，句子短，避免夸张表达和感叹号。
- 代码块要能直接复制运行，行内代码用反引号。
- 涉及生产环境风险的做法（`ddl-auto=update`、H2 Console、空密码等）要注明只适用于本地学习。
- 术语第一次出现时先解释，例如规范与实现的区别。

## 参考外部代码的红线

教程会参考真实生产项目的做法，但只提炼通用模式，不搬运具体实现。

- 不得出现来源项目的仓库名、包名、类名、方法名、表名、字段名、接口路径、业务术语、注释和配置片段。
- 不得整段复制来源代码。同一个模式必须在本项目的图书领域重新实现一遍。
- 允许写入教程的只有通用技术做法，例如"统一响应结构""调用外部服务要设超时"这类可以在任何项目中独立表述的内容。
- 涉及来源项目的内部约定、密钥、域名、环境地址时一律不写入。
- 描述某个做法时，说明它解决什么问题、代价是什么，而不是说"某个项目就是这么做的"。

## 生产标准检查清单

从第 14 篇开始，每篇文档在验证小节之后加一小节，说明本节让项目在下面哪几项上更接近生产标准，并明确哪些项仍然欠缺：

| 项目 | 含义 |
| --- | --- |
| 输入校验 | 不信任外部输入，边界上就拒绝 |
| 错误契约 | 状态码和错误响应结构稳定、可预期 |
| 事务边界 | 写操作的边界清楚，失败能回滚 |
| 可观测 | 出问题能通过日志、指标定位 |
| 配置外部化 | 环境差异通过配置解决，不改代码 |
| 安全 | 认证、授权、敏感信息不泄漏 |
| 超时与重试 | 外部依赖不会拖垮自己 |
| 幂等与并发 | 重复请求和并发修改有明确行为 |
| 测试 | 关键路径有自动化测试保护 |
| 可交付 | 能构建、能部署、能回滚 |

不要求每篇都覆盖全部项目。每篇只推进其中一到两项，并在文档里写清楚当前还缺什么。

## 验证要求

- 文档中写“会看到什么”之前，先真正运行验证过。
- 日志和响应片段要来自真实运行结果，可以删掉时间戳和线程名，不要凭印象编写。
- 无法验证的部分要在回复中说明，不要写成已确认的结论。

## 目录维护

每完成一节，下面四处必须同步更新，缺一处就算这一节没写完：

| 文件 | 要更新什么 |
| --- | --- |
| `docs/README.md` | 阶段列表、完成标志、后续学习路线 |
| `README.md`（根目录） | 学习进度表、当前接口与错误响应、代码分层图、学习文档列表、代码快照标签表、测试用例数量 |
| `docs/00-如何重现每一节代码.md` | tag 表格新增一行，以及 `git tag --list` 的示例输出 |
| `rspress.config.ts` | 侧边栏新增对应条目或分组 |

其他约定：

- 每一节的代码和文档单独提交，提交信息使用英文小写祈使句，例如 `docs: ...`、`feat: ...`、`test: ...`、`refactor: ...`。
- 代码有变化的节要建立 `lesson-NN-简短英文` 形式的 annotated tag。tag 编号按代码变化的节递增，与文档编号不一致，所以要在 `docs/00` 和根 README 里写清对应关系。
- 接口行为发生变化时，在根 README 的接口说明里注明从哪一节开始变化，例如状态码由 204 改为 404。
