# 第 13 步：参数校验和统一异常处理

## 这一节要完成什么

上一节把数据保存到了 H2，但接口还有两个明显问题。

第一个问题：新增图书时不检查内容。下面这个请求会被接受，数据库里会多出一本没有书名和作者的图书：

```bash
curl -i -X POST http://localhost:8080/api/books -H 'Content-Type: application/json' -d '{}'
```

第二个问题：查询不存在的编号时，返回的是 HTTP 200 和空响应体：

```text
HTTP/1.1 200
Content-Length: 0
```

调用方拿到 200 会认为请求成功，但响应体里什么都没有，只能自己猜发生了什么。删除不存在的编号也一样，上一节返回的是 204。

本节完成两件事：

```text
请求进入 Controller 之前
      ↓
Bean Validation 检查 title 和 author 是否为空   ← 本节新增
      ↓
Controller → Service
      ↓
Service 找不到图书时抛出 BookNotFoundException   ← 本节新增
      ↓
GlobalExceptionHandler 统一转换成 JSON           ← 本节新增
      ↓
400 或 404，响应体里写清楚原因
```

完成后，参数错误返回 400 并指出哪个字段有问题，编号不存在返回 404 并给出说明文字。

## 1. 先确认上一节的行为

保持上一节的代码运行，执行：

```bash
curl -i http://localhost:8080/api/books/99
```

实际返回：

```text
HTTP/1.1 200
Content-Length: 0
```

再执行：

```bash
curl -i -X DELETE http://localhost:8080/api/books/99
```

实际返回 204。

这两个结果都不能算错误的写法，但对调用方不友好。HTTP 已经定义了表示“资源不存在”的状态码 404，本节要开始使用它。

## 3. 在 pom.xml 添加校验依赖

打开根目录的 `pom.xml`，在 `spring-boot-starter-data-jpa` 后增加：

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-validation</artifactId>
</dependency>
```

### 为什么需要单独添加

Spring Boot 2.3 之前，`spring-boot-starter-web` 自带校验功能。2.3 之后被拆分出来，需要显式添加 `spring-boot-starter-validation`。本项目使用 2.7.18，所以必须自己加这一行。

如果不加这个依赖，`@Valid` 不会报错，但也不会真正生效，空数据仍然能保存进数据库。

### Bean Validation 和 Hibernate Validator

这里又出现了规范与实现的关系，和上一节 JPA 与 Hibernate 的关系类似。

| 名称 | 职责 |
| --- | --- |
| Bean Validation | Java 的校验规范，定义 `@NotBlank`、`@NotNull` 等注解 |
| Hibernate Validator | Bean Validation 的具体实现，真正执行检查 |
| spring-boot-starter-validation | 把上面两个和 Spring 的整合打包在一起 |

Hibernate Validator 和上一节的 Hibernate ORM 是同一个组织的两个不同项目，一个负责校验，一个负责数据库映射，不要混在一起理解。

## 5. 给 Book 添加校验注解

打开：

```text
src/main/java/com/example/bookapi/model/Book.java
```

增加 import：

```java
import javax.validation.constraints.NotBlank;
```

给两个字段加上注解：

```java
@Id
@GeneratedValue(strategy = GenerationType.IDENTITY)
private Long id;

@NotBlank(message = "书名不能为空")
private String title;

@NotBlank(message = "作者不能为空")
private String author;
```

### @NotBlank

```java
@NotBlank
```

要求字符串不是 `null`、不是空字符串、也不能只包含空格。

所以下面三种请求都会被拒绝：

```json
{}
{"title": "", "author": "赵六"}
{"title": "   ", "author": "赵六"}
```

### message

```java
@NotBlank(message = "书名不能为空")
```

校验失败时使用的说明文字。不写 `message` 时，默认文字是英文的 `must not be blank`。写清楚中文提示，调用方更容易定位问题。

### 为什么 id 不加校验

新增图书时 id 由数据库生成，客户端不需要传，Service 里还会执行 `book.setId(null)`。所以 id 不参与校验。

### 常用的校验注解

本节只用到 `@NotBlank`。下面几个以后会用到，先认识即可：

| 注解 | 作用 | 适用类型 |
| --- | --- | --- |
| `@NotNull` | 不能是 null | 任意类型 |
| `@NotBlank` | 不能是 null、空字符串或纯空格 | 字符串 |
| `@NotEmpty` | 不能是 null 或空集合、空字符串 | 字符串、集合 |
| `@Size(max = 100)` | 限制长度或元素个数 | 字符串、集合 |
| `@Min` 和 `@Max` | 限制数值范围 | 数字 |
| `@Email` | 必须是邮箱格式 | 字符串 |
| `@Pattern` | 必须匹配正则表达式 | 字符串 |

### 校验注解写在实体上的取舍

本项目直接把 `@NotBlank` 写在实体 `Book` 上，因为当前只有一个类，这样最容易看懂。

需要知道它的代价：实体同时承担了三种职责，数据库映射、JSON 结构和请求校验。真实项目通常会为请求单独建一个类，例如 `BookRequest`，把校验注解放在那个类上，实体只负责数据库。等后面接口变复杂时会再讨论这个做法。

### @NotBlank 不会改变数据库表结构

`@NotBlank` 只在 Java 层检查，不会给数据库列加约束。这是在空数据库上启动时 Hibernate 打印的建表语句：

```text
create table books (
   id bigint generated by default as identity,
    author varchar(255),
    title varchar(255),
    primary key (id)
)
```

两列都没有 `not null`。也就是说，绕过接口直接用 SQL 插入空书名仍然可以成功。接口层校验和数据库约束是两件事。

## 6. 在 Controller 使用 @Valid

打开：

```text
src/main/java/com/example/bookapi/controller/BookController.java
```

增加 import：

```java
import javax.validation.Valid;
```

给 POST 和 PUT 的请求体参数加上 `@Valid`：

```java
@PostMapping
@ResponseStatus(HttpStatus.CREATED)
public Book create(@Valid @RequestBody Book book) {
    return bookService.create(book);
}

@PutMapping("/{id}")
public Book update(@PathVariable Long id, @Valid @RequestBody Book updatedBook) {
    return bookService.update(id, updatedBook);
}
```

### @Valid 的作用

```java
public Book create(@Valid @RequestBody Book book) {
```

两个注解的先后顺序是：

```text
@RequestBody  → Jackson 把 JSON 转换成 Book 对象
      ↓
@Valid        → 检查这个 Book 对象上的校验注解
      ↓
校验通过 → 执行方法体
校验失败 → 抛出 MethodArgumentNotValidException，方法体不会执行
```

关键点：校验失败时，`create()` 方法里的代码一行都不会运行，Service 和数据库完全不会被调用。

### 只给 POST 和 PUT 加

GET 和 DELETE 没有请求体，没有需要校验的 JSON，所以不加 `@Valid`。

### @Valid 和 @Validated

以后可能看到 `@Validated`。它是 Spring 自己提供的注解，支持分组校验，也可以加在类上用于校验方法参数。当前只需要校验请求体，用 Bean Validation 规范里的 `@Valid` 就够了。

## 7. 先看默认的错误响应

到这里可以先启动一次应用，观察只加校验、还没有统一处理时会返回什么。

执行：

```bash
curl -i -X POST http://localhost:8080/api/books -H 'Content-Type: application/json' -d '{}'
```

实际返回：

```text
HTTP/1.1 400
{"timestamp":"2026-09-06T09:19:19.526+00:00","status":400,"error":"Bad Request","path":"/api/books"}
```

状态码 400 是对的，说明校验已经生效，空数据没有进入数据库。问题是响应体里没有任何字段信息，调用方不知道是书名还是作者有问题。

真正的原因只出现在服务端控制台里：

```text
WARN ... DefaultHandlerExceptionResolver : Resolved
[org.springframework.web.bind.MethodArgumentNotValidException: Validation failed for argument [0]
 ... Field error in object 'book' on field 'author': ... default message [作者不能为空]]
 ... Field error in object 'book' on field 'title': ... default message [书名不能为空]] ]
```

`作者不能为空` 和 `书名不能为空` 都在，只是留在了日志里。接下来要做的，就是把这些信息放进响应体。

顺便记住这个异常的名字：`MethodArgumentNotValidException`。可以按字面理解为“方法参数没有通过校验”。后面的处理器就是按这个类型来拦截的。

## 8. 创建 ApiError

先约定错误响应的统一结构。

在 IDEA 中：

1. 右键 `com.example.bookapi`。
2. 选择 **New → Package**。
3. 输入 `exception`。
4. 右键 `exception` 包。
5. 选择 **New → Java Class**。
6. 输入 `ApiError`。

完整代码：

```java
package com.example.bookapi.exception;

import com.fasterxml.jackson.annotation.JsonInclude;

import java.util.Map;

@JsonInclude(JsonInclude.Include.NON_NULL)
public class ApiError {

    private int status;
    private String message;
    private Map<String, String> fieldErrors;

    public ApiError(int status, String message) {
        this.status = status;
        this.message = message;
    }

    public ApiError(int status, String message, Map<String, String> fieldErrors) {
        this.status = status;
        this.message = message;
        this.fieldErrors = fieldErrors;
    }

    public int getStatus() {
        return status;
    }

    public String getMessage() {
        return message;
    }

    public Map<String, String> getFieldErrors() {
        return fieldErrors;
    }
}
```

### 三个字段的用途

| 字段 | 用途 |
| --- | --- |
| `status` | HTTP 状态码，和响应头里的状态码保持一致 |
| `message` | 一句人能读懂的说明 |
| `fieldErrors` | 字段名到错误提示的对应关系，只有参数校验失败时才有 |

### @JsonInclude

```java
@JsonInclude(JsonInclude.Include.NON_NULL)
```

告诉 Jackson：值为 `null` 的字段不要输出。

因为 404 响应用不到 `fieldErrors`，加上这个注解后，404 的响应体是干净的：

```json
{"status":404,"message":"图书不存在，编号 99"}
```

不加这个注解会多出一个没有意义的 `"fieldErrors":null`。

### 两个构造方法

一个用于只有说明文字的错误，例如 404。另一个用于需要携带字段信息的错误，例如 400。

### 为什么只有 getter

这个类只用于输出 JSON。Jackson 序列化对象时读取 getter，不需要 setter，所以不提供。

## 9. 创建 BookNotFoundException

在 `exception` 包中新建 `BookNotFoundException`：

```java
package com.example.bookapi.exception;

public class BookNotFoundException extends RuntimeException {

    public BookNotFoundException(Long id) {
        super("图书不存在，编号 " + id);
    }
}
```

### 为什么继承 RuntimeException

Java 的异常分两类：

| 类型 | 说明 | 影响 |
| --- | --- | --- |
| 受检异常 | 继承 `Exception`，例如 `IOException` | 调用方必须写 `try-catch` 或在方法上声明 `throws` |
| 运行时异常 | 继承 `RuntimeException` | 不强制处理，可以一路往上抛 |

选择 `RuntimeException` 是为了让 Service 直接抛出，Controller 不需要写任何 `try-catch`，异常会自动交给统一处理器。

### 构造方法接收 id

```java
super("图书不存在，编号 " + id);
```

`super(...)` 把这句话交给父类保存成异常信息，后面处理器用 `getMessage()` 就能取出来。把 id 拼进去，调用方能直接看到是哪个编号有问题。

### 为什么放在 exception 包

这个类不是数据库实体，也不是业务逻辑，它属于错误处理相关的代码，和 `ApiError`、处理器放在一起更容易查找。

## 10. 创建 GlobalExceptionHandler

在 `exception` 包中新建 `GlobalExceptionHandler`：

```java
package com.example.bookapi.exception;

import org.springframework.http.HttpStatus;
import org.springframework.validation.FieldError;
import org.springframework.web.bind.MethodArgumentNotValidException;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.ResponseStatus;
import org.springframework.web.bind.annotation.RestControllerAdvice;

import java.util.LinkedHashMap;
import java.util.Map;

@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(BookNotFoundException.class)
    @ResponseStatus(HttpStatus.NOT_FOUND)
    public ApiError handleBookNotFound(BookNotFoundException exception) {
        return new ApiError(HttpStatus.NOT_FOUND.value(), exception.getMessage());
    }

    @ExceptionHandler(MethodArgumentNotValidException.class)
    @ResponseStatus(HttpStatus.BAD_REQUEST)
    public ApiError handleValidationError(MethodArgumentNotValidException exception) {
        Map<String, String> fieldErrors = new LinkedHashMap<>();
        for (FieldError fieldError : exception.getBindingResult().getFieldErrors()) {
            fieldErrors.put(fieldError.getField(), fieldError.getDefaultMessage());
        }
        return new ApiError(HttpStatus.BAD_REQUEST.value(), "请求参数不正确", fieldErrors);
    }
}
```

### @RestControllerAdvice

```java
@RestControllerAdvice
```

它相当于两个注解合在一起：

```text
@ControllerAdvice   让这个类对所有 Controller 生效
@ResponseBody       让方法返回值变成响应体，而不是视图名
```

和 `@RestController` 的关系可以这样记：

| 注解 | 作用范围 |
| --- | --- |
| `@RestController` | 处理正常请求 |
| `@RestControllerAdvice` | 处理 Controller 抛出的异常 |

它同时也是一个 Spring 组件，应用启动时会被扫描并注册，不需要额外加 `@Component`。

### @ExceptionHandler

```java
@ExceptionHandler(BookNotFoundException.class)
```

声明这个方法负责处理哪种异常。Controller 方法抛出 `BookNotFoundException` 时，Spring 会找到这个方法执行。

括号里的类型决定了匹配范围。写父类型会同时匹配子类型，所以不要随手写 `Exception.class`，否则所有异常都会被同一个方法接住，反而看不清问题。

### @ResponseStatus

```java
@ResponseStatus(HttpStatus.NOT_FOUND)
```

指定响应状态码。`HttpStatus.NOT_FOUND` 就是 404，`HttpStatus.BAD_REQUEST` 就是 400。

`ApiError` 里的 `status` 字段也写同一个值，用 `HttpStatus.NOT_FOUND.value()` 取到数字 404，避免响应头和响应体不一致。

### 从异常中取出字段错误

```java
for (FieldError fieldError : exception.getBindingResult().getFieldErrors()) {
    fieldErrors.put(fieldError.getField(), fieldError.getDefaultMessage());
}
```

逐行理解：

```text
exception.getBindingResult()   拿到这次校验的全部结果
        .getFieldErrors()      只取字段级别的错误列表
fieldError.getField()          出错的字段名，例如 title
fieldError.getDefaultMessage() 注解里写的 message，例如 书名不能为空
```

循环把它们放进一个 Map，最终输出成响应体里的 `fieldErrors`。

### 为什么用 LinkedHashMap

`LinkedHashMap` 会按写入顺序保存，输出的 JSON 字段顺序和循环放入的顺序一致。换成 `HashMap` 时，输出顺序由哈希决定，同一批数据也可能忽然变样。

需要注意的是，这只保证“输出顺序等于放入顺序”。放入顺序来自 `getFieldErrors()` 返回的列表，而多个字段之间谁先谁后，Bean Validation 并没有规定，不同运行环境甚至同一台机器的不同次启动都可能不同。

所以：

- 同一个响应内部的顺序是确定的。
- 多个字段的相对先后不要当作接口约定。
- 调用方应该按字段名去取提示，例如取 `fieldErrors.title`，不要按位置取第一个。

### 这个类不需要被谁调用

和 `DataInitializer` 一样，项目里没有任何代码调用 `handleBookNotFound()`。它是 Spring 在处理请求出现异常时回调的。具体位置见本节第 17 步的请求阶段链路。

## 11. 修改 BookService

现在让 Service 在找不到图书时抛出异常，而不是返回 `null`。

打开：

```text
src/main/java/com/example/bookapi/service/BookService.java
```

增加 import：

```java
import com.example.bookapi.exception.BookNotFoundException;
```

修改三个方法：

```java
public Book findById(Long id) {
    return bookRepository.findById(id)
            .orElseThrow(() -> new BookNotFoundException(id));
}

public Book update(Long id, Book updatedBook) {
    Book book = findById(id);
    book.setTitle(updatedBook.getTitle());
    book.setAuthor(updatedBook.getAuthor());
    return bookRepository.save(book);
}

public void delete(Long id) {
    if (!bookRepository.existsById(id)) {
        throw new BookNotFoundException(id);
    }
    bookRepository.deleteById(id);
}
```

### orElse 换成 orElseThrow

上一节的写法是：

```java
return bookRepository.findById(id).orElse(null);
```

现在是：

```java
return bookRepository.findById(id)
        .orElseThrow(() -> new BookNotFoundException(id));
```

两个方法都作用在 `Optional<Book>` 上：

| 方法 | 查询到图书 | 没有查询到 |
| --- | --- | --- |
| `orElse(null)` | 返回 Book | 返回 null，调用方需要自己判断 |
| `orElseThrow(...)` | 返回 Book | 抛出括号里创建的异常 |

`() -> new BookNotFoundException(id)` 是 Java 8 的 lambda 写法，表示“需要抛异常时才创建这个对象”。查询成功时这个对象不会被创建。

### update 直接复用 findById

```java
Book book = findById(id);
```

上一节这里要先查询再判断 `null`。现在 `findById` 已经保证“要么返回图书，要么抛异常”，所以判断代码可以删掉。方法体只剩下修改字段和保存。

这是抛异常带来的直接好处：不存在的情况只在一个地方处理，其他方法都可以假设拿到的是有效对象。

### delete 的行为变化

```java
public void delete(Long id) {
    if (!bookRepository.existsById(id)) {
        throw new BookNotFoundException(id);
    }
    bookRepository.deleteById(id);
}
```

注意条件里多了一个 `!`，含义从“存在就删除”变成“不存在就抛异常”。

这是本节唯一一处接口行为变化：

| 请求 | 上一节 | 本节 |
| --- | --- | --- |
| DELETE 一个存在的编号 | 204 | 204 |
| DELETE 一个不存在的编号 | 204 | 404 |
| 重复 DELETE 同一个编号 | 第二次仍然 204 | 第二次 404 |

两种做法在真实项目里都有人用。本课程选择 404，因为这样 GET、PUT、DELETE 三个按编号操作的接口行为一致，调用方只需要记一条规则：编号不存在就是 404。

HTTP/1.1 400

```

编号 1 的图书不会被修改，因为 Controller 方法体没有执行。

### 校验失败时控制台没有 SQL

执行上面几条 400 请求时，IDEA 控制台不会打印 Hibernate 语句。

原因是校验发生在进入 Controller 方法之前，请求根本没有到达 Service 和 Repository。这一点可以直接在 Run 窗口确认：只有校验通过的请求才会产生 select、insert 或 update。

HTTP/1.1 404
{"status":404,"message":"图书不存在，编号 99"}
```

修改不存在的编号：

```bash
curl -i -X PUT http://localhost:8080/api/books/99 -H 'Content-Type: application/json' -d '{"title":"测试","author":"测试"}'
```

预期返回：

```text
HTTP/1.1 404
{"status":404,"message":"图书不存在，编号 99"}
```

删除不存在的编号：

```bash
curl -i -X DELETE http://localhost:8080/api/books/99
```

预期返回：

```text
HTTP/1.1 404
{"status":404,"message":"图书不存在，编号 99"}
```

三个接口的错误响应结构完全一样，因为它们抛出的都是 `BookNotFoundException`，都由同一个处理器方法转换。

### 404 请求会产生 SQL

和 400 不同，404 的请求已经进入了 Service，所以控制台能看到查询语句：

```text
GET 不存在的编号     → select ... from books where id=?
DELETE 不存在的编号  → select count(*) from books where id=?
```

先查询、发现没有、再抛异常，这就是 404 与 400 在链路上的区别。

## 14. 验证正常请求没有受影响

查询全部：

```bash
curl -i http://localhost:8080/api/books
```

正常新增：

```bash
curl -i -X POST http://localhost:8080/api/books -H 'Content-Type: application/json' -d '{"title":"数据库入门","author":"赵六"}'
```

预期仍然是 201 和数据库自动生成的编号。在一个空数据库上验证时返回的是：

```json
{"id":4,"title":"数据库入门","author":"赵六"}
```

你的数据库里已经有上一节练习的数据，所以拿到的编号可能更大，这是正常的。

删除刚才新增的图书，把命令末尾的编号换成上一步实际返回的 id：

```bash
curl -i -X DELETE http://localhost:8080/api/books/4
```

预期返回 204，响应体为空。

校验和异常处理只在出错时介入，正常流程和上一节完全一致。

## 15. 还有两种 400 没有被统一处理

有两类请求错误不会走 `GlobalExceptionHandler`。

JSON 格式本身有问题：

```bash
curl -i -X POST http://localhost:8080/api/books -H 'Content-Type: application/json' -d '{"title":'
```

实际返回：

```text
HTTP/1.1 400
{"timestamp":"2026-09-06T09:17:18.299+00:00","status":400,"error":"Bad Request","path":"/api/books"}
```

编号不是数字：

```bash
curl -i http://localhost:8080/api/books/abc
```

实际返回：

```text
HTTP/1.1 400
{"timestamp":"2026-09-06T09:17:18.320+00:00","status":400,"error":"Bad Request","path":"/api/books/abc"}
```

这两种情况的状态码是对的，但响应体结构和我们定义的 `ApiError` 不一样。

原因是它们抛出的是另外两种异常：

| 请求问题 | 异常类型 | 谁处理 |
| --- | --- | --- |
| 缺少字段或字段为空 | `MethodArgumentNotValidException` | 本节的 `GlobalExceptionHandler` |
| JSON 语法错误 | `HttpMessageNotReadableException` | Spring 默认的处理器 |
| 路径参数类型不对 | `MethodArgumentTypeMismatchException` | Spring 默认的处理器 |

`@ExceptionHandler` 只处理声明过的类型，没声明的仍然由 Spring 默认逻辑兜底。要让这两种错误也返回统一结构，只需要在 `GlobalExceptionHandler` 里再加对应的方法。本节先不加，保持代码量可控，也让“声明了才会被接管”这一点更清楚。

## 17. 完整调用链路

### 启动阶段新增了什么

上一节的启动流程不变，本节只是多了两件事：

```text
... 扫描 com.example.bookapi 及子包
      ↓
除了 Controller、Service、DataInitializer
还扫描到 GlobalExceptionHandler(@RestControllerAdvice)   ← 本节新增
      ↓
Spring 记录下它声明的两个 @ExceptionHandler 方法
  ├─ BookNotFoundException        → handleBookNotFound
  └─ MethodArgumentNotValidException → handleValidationError
      ↓
自动配置检测到 classpath 中有 Hibernate Validator
创建校验器，供 @Valid 使用                                ← 本节新增
      ↓
... 后面的连接池、建表、Tomcat、CommandLineRunner 与上一节相同
```

这两件事都发生在请求到来之前。因此处理请求时，Spring 不需要临时查找处理器，直接按异常类型取用已经登记好的方法。

### 请求阶段的三条分支

同一个 POST 请求，现在有三种可能的走向：

```text
curl 发出请求
      ↓
Tomcat → DispatcherServlet 找到 BookController 的方法
      ↓
@RequestBody：Jackson 把 JSON 转换成 Book 对象
      ↓
   JSON 语法错误？ ──是──→ HttpMessageNotReadableException
      ↓ 否                        ↓
@Valid：Hibernate Validator   Spring 默认处理器 → 400，默认结构
检查 @NotBlank
      ↓
   校验失败？ ──是──→ MethodArgumentNotValidException
      ↓ 否                 ↓
                    GlobalExceptionHandler.handleValidationError
                           ↓
                    读取 getFieldErrors()，组装 ApiError
                           ↓
                    Jackson 输出 → 400 + fieldErrors
                    这条分支完全不碰数据库
      ↓
执行 Controller 方法体 → BookService
      ↓
   Service 需要的图书不存在？ ──是──→ 先执行了 select，再抛 BookNotFoundException
      ↓ 否                                  ↓
Repository → Hibernate → H2            GlobalExceptionHandler.handleBookNotFound
      ↓                                     ↓
正常结果逐层返回                        ApiError → 404 + message
      ↓
Jackson 转换成 JSON → 200 或 201
```

三条分支的分界点很清楚：

| 出错位置 | 是否执行 Controller 方法体 | 是否访问数据库 | 响应 |
| --- | --- | --- | --- |
| JSON 转换阶段 | 否 | 否 | 400，Spring 默认结构 |
| `@Valid` 校验阶段 | 否 | 否 | 400，`ApiError` 结构 |
| Service 查询阶段 | 是 | 是 | 404，`ApiError` 结构 |
| 没有出错 | 是 | 是 | 200 或 201 |

### 异常是怎么变成 JSON 的

`BookNotFoundException` 在 Service 里抛出后，没有任何代码捕获它，它会一路向上传递：

```text
BookService.findById 抛出 BookNotFoundException
      ↓
BookController.findById 没有 try-catch，异常继续向上
      ↓
DispatcherServlet 捕获到这个异常
      ↓
交给 ExceptionHandlerExceptionResolver
      ↓
按异常类型查找已登记的 @ExceptionHandler 方法
      ↓
匹配到 GlobalExceptionHandler.handleBookNotFound
      ↓
执行方法，得到 ApiError 对象
      ↓
读取方法上的 @ResponseStatus，把状态码设为 404
      ↓
因为是 @RestControllerAdvice，Jackson 把 ApiError 转换成 JSON
      ↓
Tomcat 返回 404 和响应体
```

所以 Controller 和 Service 都不需要写 `try-catch`，错误处理集中在一个类里。

### 每一层负责什么

和上一节相比，多了两层：

| 层次 | 主要职责 |
| --- | --- |
| Jackson | JSON 与 Java 对象互相转换 |
| Hibernate Validator | 按 `@NotBlank` 等注解检查请求对象 |
| Controller | 处理地址、参数和响应状态 |
| Service | 组织业务步骤，找不到数据时抛出异常 |
| GlobalExceptionHandler | 把异常统一转换成 `ApiError` 和状态码 |
| Repository 及以下 | 与上一节相同 |

### 本节新增类的引用与调用关系

本节新增的三个类，没有一个是被业务代码调用的。它们的关系值得单独列清楚：

| 类 | 谁引用它 | 运行期谁调用它 | 触发时机 |
| --- | --- | --- | --- |
| `BookNotFoundException` | `BookService` 里创建它的两处代码 | 不需要被调用，只需要被抛出 | Service 查不到对应编号时 |
| `ApiError` | 只有 `GlobalExceptionHandler`，两处作为返回类型、两处 `new` | 不需要被调用，只被创建和序列化 | 处理器方法返回后，Jackson 读它的 getter |
| `GlobalExceptionHandler` | 没有任何项目代码引用它 | Spring 的 `ExceptionHandlerExceptionResolver` | Controller 抛出已登记类型的异常时 |

三点容易误解的地方：

- `ApiError` 在整个项目里只被一个文件引用，看起来像没人用的类。它的职责就是描述错误响应的形状，不需要到处引用。
- `GlobalExceptionHandler` 连引用都没有。它靠 `@RestControllerAdvice` 被扫描进容器，靠 `@ExceptionHandler` 被登记进异常处理表，然后等着被回调。这一点和第 12 篇的 `DataInitializer` 是同一种写法。
- `BookController` 和 `BookService` 都不知道 `ApiError` 存在。业务代码只负责抛出有意义的异常，错误响应长什么样由处理器统一决定。删掉 `GlobalExceptionHandler` 时，业务代码一行都不用改，只是响应会退回 Spring 的默认结构。

### 没有登记的异常走哪条路

Spring 捕获到异常后，按固定顺序询问三个处理器：

```text
Controller 抛出异常
      ↓
1. ExceptionHandlerExceptionResolver
   查启动时登记的表，本项目登记了两条
   命中 → 执行我们的方法，返回 ApiError
      ↓ 表里没有
2. ResponseStatusExceptionResolver
   看异常类上有没有 @ResponseStatus 注解
      ↓ 没有
3. DefaultHandlerExceptionResolver
   Spring 内置的一批标准异常，只设置状态码，不生成响应体
   JSON 语法错误、路径参数类型不对都在这一步变成 400
      ↓ 都不认识
4. 没有人处理，异常抛给 Servlet 容器
      ↓
状态码触发容器的错误处理，请求转到内置的 /error
      ↓
返回 {"timestamp":...,"status":...,"error":...,"path":...}
未知异常在这里变成 500，并在控制台打印完整堆栈
```

第 15 步看到的两种默认结构，就是走到第 3 步和第 4 步的结果。这也说明了一件事：`@ExceptionHandler` 是“声明了才接管”，没声明的异常不会凭空得到统一结构。

### 用真实响应对照这条链路

下面四条响应来自本节的实际验证，可以逐条对应上面的分支：

```text
POST {}                          → 400 {"status":400,"message":"请求参数不正确",
                                        "fieldErrors":{"title":"书名不能为空","author":"作者不能为空"}}
                                   校验分支，控制台没有 SQL，两个字段的顺序可能互换
GET  /api/books/99               → 404 {"status":404,"message":"图书不存在，编号 99"}
                                   Service 分支，控制台有一条 select
DELETE /api/books/99             → 404 {"status":404,"message":"图书不存在，编号 99"}
                                   Service 分支，控制台有一条 select count(*)
POST 正确的 JSON                  → 201 {"id":4,"title":"数据库入门","author":"赵六"}
                                   正常分支，控制台有一条 insert
```

## 成功标准

- Maven 能加载 `spring-boot-starter-validation`。
- POST 空 JSON 返回 400，响应体里同时给出 title 和 author 的提示，两者顺序不作要求。
- 书名只有空格时也返回 400。
- GET、PUT、DELETE 不存在的编号都返回 404，响应体结构一致。
- 正常的查询、新增、修改、删除行为与上一节相同。
- 能说明 `@Valid` 校验失败时为什么控制台没有 SQL。
- 能说明 404 与 400 在链路上的位置差异。
- 能说明 `GlobalExceptionHandler` 里的方法是被谁调用的。
- 能解释 `orElse(null)` 和 `orElseThrow(...)` 的区别。

## 常见问题

### javax.validation 显示红色

确认 `pom.xml` 已添加 `spring-boot-starter-validation`，然后在 Maven 窗口点击刷新并等待下载完成。

本项目使用 Spring Boot 2.7，请导入 `javax.validation`，不是 `jakarta.validation`。

### 加了 @NotBlank 但空数据仍然能保存

按顺序检查三点：

1. `pom.xml` 是否添加了 `spring-boot-starter-validation`。
2. Controller 的参数上是否写了 `@Valid`。
3. 是否重新启动了应用。

只加注解不加 `@Valid`，校验不会执行。

### fieldErrors 里字段顺序和文档不一致

正常现象。校验框架返回多个字段错误时不保证先后顺序，重启应用后顺序也可能变化。只要两个字段的提示都在，就是正确的。详见第 10 步关于 `LinkedHashMap` 的说明。

### 返回 400 但响应体不是 ApiError 结构

先确认发送的 JSON 语法正确。JSON 少了引号或括号时抛出的是 `HttpMessageNotReadableException`，由 Spring 默认处理，见本节第 15 步。

### 返回 500 而不是 404

说明 `BookNotFoundException` 没有被处理器接住。检查：

1. `GlobalExceptionHandler` 上是否有 `@RestControllerAdvice`。
2. 类是否位于 `com.example.bookapi` 的子包中，能被扫描到。
3. `@ExceptionHandler` 括号里的类型是否写成了 `BookNotFoundException.class`。

### 响应体里出现 "fieldErrors":null

确认 `ApiError` 类上有：

```java
@JsonInclude(JsonInclude.Include.NON_NULL)
```

并确认 import 的是 `com.fasterxml.jackson.annotation.JsonInclude`。

### 删除不存在的编号返回 204

说明 `delete` 方法还是上一节的写法。确认条件里有 `!`：

```java
if (!bookRepository.existsById(id)) {
    throw new BookNotFoundException(id);
}
```

### 提示信息显示成 must not be blank

说明注解里没有写 `message`，用的是默认英文提示。按第 5 步补上：

```java
@NotBlank(message = "书名不能为空")
```

### 端口 8080 被占用

可能仍有旧的 Spring Boot 进程在运行。在 IDEA Run 窗口停止旧进程，再重新启动。
