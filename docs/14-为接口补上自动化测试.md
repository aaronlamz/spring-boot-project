# 第 14 步：为接口补上自动化测试

## 这一节要完成什么

到上一节为止，验证接口的方式一直是手工执行 `curl`。这种方式有三个问题。

第一，慢。前面几节累积下来，要完整验证一遍需要十几条命令。

第二，容易漏。正常路径通常会试，400 和 404 这些错误路径最容易忘记验证。

第三，改代码之后不知道有没有弄坏别的地方。上一节把 `delete` 的行为从返回 204 改成 404，靠的是人工记住要重新试一遍。

本节给现有代码补上自动化测试，把这些验证固定下来：

```text
一条命令 mvn test
      ↓
自动启动需要的部分组件
      ↓
按事先写好的用例调用代码
      ↓
逐条检查返回值和状态码
      ↓
全部通过才算改动安全
```

完成后，项目会有 16 个测试用例，覆盖 Service、Repository 和 Controller 三层，包含 400 和 404 两条错误路径。

## 1. 测试代码放在哪里

项目里已经有这两个目录：

```text
src/main/java     业务代码，会被打进最终的 jar 包
src/test/java     测试代码，只在开发和构建时使用
src/main/resources  运行时的配置
src/test/resources  测试专用配置，第 12 步创建过
```

这是 Maven 的固定约定。测试代码不会进入交付物，所以可以放心在测试里写死数据。

测试类的包结构和被测类保持一致：

```text
src/main/java/com/example/bookapi/service/BookService.java
src/test/java/com/example/bookapi/service/BookServiceTest.java
```

好处是两个文件在 IDEA 里挨着显示，而且测试类能访问被测类的包内成员。

类名以 `Test` 结尾也是约定。Maven 的测试插件默认只运行 `Test` 开头或结尾的类，名字写错会导致测试根本没被执行，而构建仍然显示成功。

## 2. 依赖已经有了

`pom.xml` 从第一节起就有这段：

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-test</artifactId>
    <scope>test</scope>
</dependency>
```

本节不需要添加任何依赖。这个 Starter 里包含了要用到的全部工具：

| 工具 | 作用 |
| --- | --- |
| JUnit 5 | 测试框架，负责发现并运行测试方法 |
| AssertJ | 断言库，提供 `assertThat(...)` 这类可读性好的检查写法 |
| Mockito | 制造替身对象，让被测类脱离真实依赖 |
| Spring Test | 提供 `@DataJpaTest`、`@WebMvcTest` 等测试专用注解 |
| MockMvc | 不启动 Tomcat 也能发起 HTTP 请求的测试工具 |
| JSONPath | 用 `$.id` 这样的表达式检查 JSON 里的某个字段 |

`<scope>test</scope>` 表示这些库只在测试时可用。在 `src/main/java` 里 import Mockito 会直接编译失败，这是有意的限制，避免测试工具混进生产代码。

## 3. 先分清三种测试范围

后面三个测试类分别属于三种不同范围，先建立整体印象。

| 范围 | 启动了什么 | 本节例子 | 单个用例耗时 |
| --- | --- | --- | --- |
| 单元测试 | 什么都不启动，只 new 出被测类 | `BookServiceTest` | 毫秒级 |
| 切片测试 | 只启动某一层需要的组件 | `BookRepositoryTest`、`BookControllerTest` | 百毫秒到秒级 |
| 集成测试 | 启动整个应用 | 已有的 `BookApiApplicationTests` | 秒级 |

选择原则是：能用小范围验证的，就不要启动大范围。范围越小跑得越快，失败时定位也越准。

一个直观的判断方式：如果你要验证的是"这段 if 判断写对了吗"，用单元测试；如果要验证的是"这段代码和框架配合起来对吗"，用切片测试。

## 4. Service 的单元测试

新建：

```text
src/test/java/com/example/bookapi/service/BookServiceTest.java
```

完整代码：

```java
package com.example.bookapi.service;

import com.example.bookapi.exception.BookNotFoundException;
import com.example.bookapi.model.Book;
import com.example.bookapi.repository.BookRepository;
import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.extension.ExtendWith;
import org.mockito.ArgumentCaptor;
import org.mockito.InjectMocks;
import org.mockito.Mock;
import org.mockito.junit.jupiter.MockitoExtension;

import java.util.Optional;

import static org.assertj.core.api.Assertions.assertThat;
import static org.assertj.core.api.Assertions.assertThatThrownBy;
import static org.mockito.ArgumentMatchers.any;
import static org.mockito.ArgumentMatchers.anyLong;
import static org.mockito.Mockito.never;
import static org.mockito.Mockito.verify;
import static org.mockito.Mockito.when;

@ExtendWith(MockitoExtension.class)
class BookServiceTest {

    @Mock
    private BookRepository bookRepository;

    @InjectMocks
    private BookService bookService;

    @Test
    void findByIdReturnsBookWhenIdExists() {
        Book stored = new Book(1L, "Spring Boot 入门", "张三");
        when(bookRepository.findById(1L)).thenReturn(Optional.of(stored));

        Book found = bookService.findById(1L);

        assertThat(found.getId()).isEqualTo(1L);
        assertThat(found.getTitle()).isEqualTo("Spring Boot 入门");
    }

    @Test
    void findByIdThrowsWhenIdDoesNotExist() {
        when(bookRepository.findById(99L)).thenReturn(Optional.empty());

        assertThatThrownBy(() -> bookService.findById(99L))
                .isInstanceOf(BookNotFoundException.class)
                .hasMessage("图书不存在，编号 99");
    }

    @Test
    void createIgnoresIdSentByClient() {
        when(bookRepository.save(any(Book.class))).thenAnswer(call -> call.getArgument(0));

        bookService.create(new Book(123L, "数据库入门", "赵六"));

        ArgumentCaptor<Book> saved = ArgumentCaptor.forClass(Book.class);
        verify(bookRepository).save(saved.capture());
        assertThat(saved.getValue().getId()).isNull();
    }

    @Test
    void updateWritesNewTitleAndAuthor() {
        Book stored = new Book(1L, "旧书名", "张三");
        when(bookRepository.findById(1L)).thenReturn(Optional.of(stored));
        when(bookRepository.save(any(Book.class))).thenAnswer(call -> call.getArgument(0));

        Book updated = bookService.update(1L, new Book(null, "新书名", "李四"));

        assertThat(updated.getId()).isEqualTo(1L);
        assertThat(updated.getTitle()).isEqualTo("新书名");
        assertThat(updated.getAuthor()).isEqualTo("李四");
    }

    @Test
    void deleteDoesNotTouchRepositoryWhenIdDoesNotExist() {
        when(bookRepository.existsById(99L)).thenReturn(false);

        assertThatThrownBy(() -> bookService.delete(99L))
                .isInstanceOf(BookNotFoundException.class);

        verify(bookRepository, never()).deleteById(anyLong());
    }
}
```

### 这个类的作用和调用关系

- 作用：验证 `BookService` 的业务判断是否正确，不涉及数据库。
- 编译期引用：它引用 `BookService`、`BookRepository`、`Book`、`BookNotFoundException`。反过来没有任何代码引用这个测试类。
- 对象从哪来：`bookService` 由 Mockito 创建，`bookRepository` 是 Mockito 造的替身，都不经过 Spring 容器。
- 运行期触发：由 JUnit 5 引擎调用带 `@Test` 的方法。执行 `mvn test` 或在 IDEA 中点绿色三角时触发。
- 去掉会怎样：程序功能不变，只是失去这层保护。

### @ExtendWith(MockitoExtension.class)

```java
@ExtendWith(MockitoExtension.class)
```

告诉 JUnit：运行这个类之前，先让 Mockito 介入，把 `@Mock` 和 `@InjectMocks` 标记的字段准备好。

没有这一行，两个字段都会是 `null`，测试一开始就抛空指针。

### @Mock 和 @InjectMocks

```java
@Mock
private BookRepository bookRepository;

@InjectMocks
private BookService bookService;
```

`@Mock` 创建一个假的 `BookRepository`。它实现了接口的全部方法，但方法体都是空的，返回类型的默认值（对象返回 `null`，`boolean` 返回 `false`）。

`@InjectMocks` 创建真实的 `BookService`，并把上面那个假的 Repository 通过构造方法塞进去。这里能塞进去，正是因为 `BookService` 用的是构造器注入。

结果是：

```text
真实的 BookService  ←  假的 BookRepository
       ↑                      ↑
   被测对象              可以随意控制返回值
```

为什么要用假的？因为这一层要验证的是业务判断，不是数据库。用假的 Repository 有三个好处：不需要启动数据库，跑得极快；可以精确制造"查不到数据"这种场景；测试结果不受数据库里现有数据影响。

### when 和 thenReturn

```java
when(bookRepository.findById(99L)).thenReturn(Optional.empty());
```

读作：当有人用参数 99 调用 `findById` 时，返回一个空的 `Optional`。

这一行就是在制造"数据库里没有编号 99"这个场景。真实数据库里要构造这个场景得先确认没有这条数据，用替身则一行搞定。

注意参数要对上。如果被测代码实际用 `findById(100L)` 去查，这条设定不会命中，会返回默认值 `null`。

### thenAnswer

```java
when(bookRepository.save(any(Book.class))).thenAnswer(call -> call.getArgument(0));
```

`thenReturn` 返回固定值，`thenAnswer` 可以根据调用时的实际参数决定返回什么。这里的意思是：把传进来的第一个参数原样返回。

真实的 `save()` 会返回带数据库生成 id 的对象。测试里我们只关心传进去的对象对不对，所以原样返回最省事。

`any(Book.class)` 表示不限定具体是哪个 Book 对象。

### ArgumentCaptor

```java
ArgumentCaptor<Book> saved = ArgumentCaptor.forClass(Book.class);
verify(bookRepository).save(saved.capture());
assertThat(saved.getValue().getId()).isNull();
```

这三行解决一个问题：怎么检查"传给 `save()` 的那个对象"长什么样。

`ArgumentCaptor` 像一个取样器，把实际传入的参数留下来，后面用 `getValue()` 取出检查。

这个用例验证的是第 13 步 `create()` 里那行 `book.setId(null)`。客户端故意传了 id 为 123 的对象，如果那一行被误删，捕获到的 id 就不是 null，测试立刻失败。

### verify 和 never

```java
verify(bookRepository).save(...);                        // 必须被调用过一次
verify(bookRepository, never()).deleteById(anyLong());   // 一次都不能被调用
```

断言分两类：一类检查返回值，一类检查"有没有调用某个方法"。

`never()` 这个用例特别有价值。它验证的是：编号不存在时抛出异常，并且真的没有执行删除。如果代码写成先删除再判断，返回的状态码可能仍然正确，但行为已经错了，只有这种断言能发现。

### assertThatThrownBy

```java
assertThatThrownBy(() -> bookService.findById(99L))
        .isInstanceOf(BookNotFoundException.class)
        .hasMessage("图书不存在，编号 99");
```

用于验证"这段代码应该抛异常"。它检查两件事：异常类型对不对，异常消息对不对。

括号里的 `() -> ...` 是 Java 8 的 lambda，表示"这段代码待会儿再执行"。必须写成 lambda，否则异常会直接把测试方法中断，而不是被捕获检查。

如果这行代码没有抛异常，测试同样失败。

### 数字为什么写成 1L 和 99L

测试里出现了不少带 `L` 的数字：

```java
new Book(1L, "Spring Boot 入门", "张三")
when(bookRepository.findById(99L))
assertThat(updated.getId()).isEqualTo(1L);
```

原因和第 6 篇讲过的一样：`L` 表示这是 `long` 类型的数字，而这些位置要求的类型都是 `Long`。写成 `1` 会因为 `int` 无法直接变成 `Long` 而编译失败。

对比一下第 6 步 Controller 测试里的这一行，它反而不能带 `L`：

```java
.andExpect(jsonPath("$.id").value(4));
```

这里比较的不是 Java 方法参数，而是响应体里解析出来的 JSON 数字。JSON 里的 `4` 被解析成 `Integer`，写成 `4L` 会因为类型不一致导致断言失败。

判断依据就是这个位置要的是什么类型：

| 位置 | 类型来自哪里 | 写法 |
| --- | --- | --- |
| `new Book(...)` 的第一个参数 | 构造方法声明的 `Long` | `1L` |
| `findById(...)` 的参数 | 方法声明的 `Long` | `99L` |
| `isEqualTo(...)` 比较 `getId()` | `getId()` 返回的 `Long` | `1L` |
| `jsonPath(...).value(...)` | JSON 解析出的 `Integer` | `4` |

### 测试方法为什么不写 public

```java
@Test
void findByIdReturnsBookWhenIdExists() {
```

JUnit 5 允许测试类和测试方法不加 `public`。方法名直接用一句话描述预期行为，测试报告里显示的就是这个名字，出错时能一眼看出坏了哪条规则。

## 5. Repository 的切片测试

新建：

```text
src/test/java/com/example/bookapi/repository/BookRepositoryTest.java
```

完整代码：

```java
package com.example.bookapi.repository;

import com.example.bookapi.model.Book;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.orm.jpa.DataJpaTest;

import java.util.Optional;

import static org.assertj.core.api.Assertions.assertThat;

@DataJpaTest
class BookRepositoryTest {

    @Autowired
    private BookRepository bookRepository;

    @Test
    void databaseStartsEmpty() {
        assertThat(bookRepository.count()).isZero();
    }

    @Test
    void saveGeneratesId() {
        Book saved = bookRepository.save(new Book(null, "Spring Boot 入门", "张三"));

        assertThat(saved.getId()).isNotNull();
        assertThat(bookRepository.count()).isEqualTo(1);
    }

    @Test
    void findByIdReturnsEmptyOptionalWhenRowIsMissing() {
        Optional<Book> found = bookRepository.findById(99L);

        assertThat(found).isEmpty();
    }

    @Test
    void deleteByIdRemovesRow() {
        Book saved = bookRepository.save(new Book(null, "Java 核心技术", "李四"));

        bookRepository.deleteById(saved.getId());

        assertThat(bookRepository.existsById(saved.getId())).isFalse();
    }
}
```

### 这个类的作用和调用关系

- 作用：验证实体映射和数据库操作真的能工作，例如主键是否由数据库生成。
- 编译期引用：引用 `BookRepository` 和 `Book`，没有任何代码引用它。
- 对象从哪来：`bookRepository` 由 Spring 注入。这里注入的是第 12 步讲过的代理对象，不是替身。
- 运行期触发：JUnit 调用测试方法，Spring 在此之前先启动一个只包含 JPA 相关组件的容器。
- 去掉会怎样：功能不变，但 `@Entity`、`@GeneratedValue` 这类映射写错时，只能等运行应用才会发现。

### @DataJpaTest 启动了什么

```java
@DataJpaTest
```

它只启动数据访问需要的部分：数据源、Hibernate、Repository 代理、事务管理。

不启动的部分包括：Tomcat、`BookController`、`BookService`、`DataInitializer`、`GlobalExceptionHandler`。所以这个测试跑得比启动整个应用快，也不会因为 Controller 有问题而失败。

### 为什么这里可以断言数据库是空的

`databaseStartsEmpty` 断言表里一行数据都没有，看起来和第 12 步的 `DataInitializer` 冲突。实际不冲突，因为 `@DataJpaTest` 做了两件事。

第一件事，它换掉了数据源。测试日志里有这一行：

```text
INFO o.s.b.t.a.j.TestDatabaseAutoConfiguration$EmbeddedDataSourceBeanFactoryPostProcessor
     - Replacing 'dataSource' DataSource bean with embedded version
```

意思是：忽略配置文件里写的数据库地址，临时换成一个新建的内存数据库。所以 `src/test/resources/application.properties` 里的 `jdbc:h2:mem:bookdb-test` 在这个测试里没有被使用，其他测试往那个库里插过什么数据都影响不到这里。

第二件事，它给每个测试方法套了一个事务，方法结束后自动回滚。

回滚这一点可以自己验证。`saveGeneratesId` 里插了一条数据并断言 `count()` 等于 1，而 `databaseStartsEmpty` 断言 `count()` 等于 0，两个用例同时通过，说明第一个用例插入的数据在方法结束时被撤销了。如果不回滚，两个用例必然有一个失败。

这就是切片测试敢用真实数据库的原因：每个用例都在自己的干净环境里跑。

### @Autowired 在测试里的用法

```java
@Autowired
private BookRepository bookRepository;
```

业务代码里我们一直用构造器注入。测试类不需要自己 new，实例由 Spring 创建，所以直接在字段上写 `@Autowired` 更简单，这在测试代码里是可以接受的写法。

### 这一层验证的是什么

四个用例分别对应四件容易出错的事：

| 用例 | 验证的事实 |
| --- | --- |
| `databaseStartsEmpty` | 测试环境是干净的，后面的断言才可信 |
| `saveGeneratesId` | `@GeneratedValue` 生效，id 由数据库生成并写回对象 |
| `findByIdReturnsEmptyOptionalWhenRowIsMissing` | 查不到时返回空 `Optional`，不是 null |
| `deleteByIdRemovesRow` | 删除真的作用到了数据库 |

## 6. Controller 的切片测试

新建：

```text
src/test/java/com/example/bookapi/controller/BookControllerTest.java
```

完整代码：

```java
package com.example.bookapi.controller;

import com.example.bookapi.exception.BookNotFoundException;
import com.example.bookapi.model.Book;
import com.example.bookapi.service.BookService;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.web.servlet.WebMvcTest;
import org.springframework.boot.test.mock.mockito.MockBean;
import org.springframework.http.MediaType;
import org.springframework.test.web.servlet.MockMvc;

import java.util.Arrays;

import static org.mockito.ArgumentMatchers.any;
import static org.mockito.ArgumentMatchers.anyLong;
import static org.mockito.BDDMockito.given;
import static org.mockito.Mockito.never;
import static org.mockito.Mockito.verify;
import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.delete;
import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.get;
import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.post;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.jsonPath;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.status;

@WebMvcTest(BookController.class)
class BookControllerTest {

    @Autowired
    private MockMvc mockMvc;

    @MockBean
    private BookService bookService;

    @Test
    void findAllReturnsJsonArray() throws Exception {
        given(bookService.findAll()).willReturn(Arrays.asList(
                new Book(1L, "Spring Boot 入门", "张三"),
                new Book(2L, "Java 核心技术", "李四")));

        mockMvc.perform(get("/api/books"))
                .andExpect(status().isOk())
                .andExpect(jsonPath("$.length()").value(2))
                .andExpect(jsonPath("$[0].title").value("Spring Boot 入门"));
    }

    @Test
    void createReturns201WithGeneratedId() throws Exception {
        given(bookService.create(any(Book.class)))
                .willReturn(new Book(4L, "数据库入门", "赵六"));

        mockMvc.perform(post("/api/books")
                        .contentType(MediaType.APPLICATION_JSON)
                        .content("{\"title\":\"数据库入门\",\"author\":\"赵六\"}"))
                .andExpect(status().isCreated())
                .andExpect(jsonPath("$.id").value(4));
    }

    @Test
    void createReturns400AndSkipsServiceWhenTitleIsBlank() throws Exception {
        mockMvc.perform(post("/api/books")
                        .contentType(MediaType.APPLICATION_JSON)
                        .content("{\"title\":\"   \",\"author\":\"赵六\"}"))
                .andExpect(status().isBadRequest())
                .andExpect(jsonPath("$.status").value(400))
                .andExpect(jsonPath("$.fieldErrors.title").value("书名不能为空"));

        verify(bookService, never()).create(any(Book.class));
    }

    @Test
    void findByIdReturns404WhenServiceThrows() throws Exception {
        given(bookService.findById(99L)).willThrow(new BookNotFoundException(99L));

        mockMvc.perform(get("/api/books/99"))
                .andExpect(status().isNotFound())
                .andExpect(jsonPath("$.status").value(404))
                .andExpect(jsonPath("$.message").value("图书不存在，编号 99"))
                .andExpect(jsonPath("$.fieldErrors").doesNotExist());
    }

    @Test
    void deleteReturns204() throws Exception {
        mockMvc.perform(delete("/api/books/1"))
                .andExpect(status().isNoContent());

        verify(bookService).delete(1L);
    }

    @Test
    void pathVariableThatIsNotANumberReturns400() throws Exception {
        mockMvc.perform(get("/api/books/abc"))
                .andExpect(status().isBadRequest());

        verify(bookService, never()).findById(anyLong());
    }
}
```

### 这个类的作用和调用关系

- 作用：验证 HTTP 层的行为，包括地址映射、状态码、JSON 结构、参数校验和异常转换。
- 编译期引用：引用 `BookController`、`BookService`、`Book`、`BookNotFoundException`。
- 对象从哪来：`mockMvc` 由 Spring 注入；`bookService` 是替身，由 `@MockBean` 创建后放进容器，替换掉真实的 Bean。
- 运行期触发：JUnit 调用测试方法，方法里通过 `mockMvc` 发起模拟请求，请求由 Spring MVC 的完整处理流程接手。
- 去掉会怎样：功能不变，但状态码、JSON 字段名这类接口契约被改坏时不会有任何提示。

### @WebMvcTest

```java
@WebMvcTest(BookController.class)
```

只启动 Web 层，并且只加载括号里指定的那个 Controller。

启动的部分：Spring MVC 的地址映射、参数解析、Jackson、校验器、异常处理器。

不启动的部分：Tomcat、数据源、Hibernate、Repository。这也意味着 `BookService` 这个依赖必须由测试自己提供，否则容器会因为缺少 Bean 而启动失败。

### @MockBean 和 @Mock 的区别

```java
@MockBean
private BookService bookService;
```

两个注解都创建替身，区别在于放到哪里：

| 注解 | 谁创建替身 | 替身放在哪 | 用在什么场景 |
| --- | --- | --- | --- |
| `@Mock` | Mockito | 只在测试类字段里 | 不启动 Spring 的单元测试 |
| `@MockBean` | Spring Boot Test | 放进 Spring 容器，顶替真实 Bean | 启动了 Spring 的切片或集成测试 |

这里必须用 `@MockBean`。因为 `BookController` 是由容器创建的，它的构造方法要从容器里取 `BookService`。只有把替身放进容器，才能被注入进去。

用替身的收益在这里特别明显：Controller 层的测试完全不碰数据库，跑一个用例是毫秒级的，而且可以随意制造"Service 抛异常"这种场景。

### given 和 willReturn

```java
given(bookService.findAll()).willReturn(...);
given(bookService.findById(99L)).willThrow(new BookNotFoundException(99L));
```

`given/willReturn` 和前面 `when/thenReturn` 是同一个功能的两种写法，来自 Mockito 的两套 API，行为完全一致。测试里可以任选一种，同一个项目保持统一即可。

`willThrow` 用来让替身抛异常，这样才能测到 404 的转换过程。

### MockMvc 的三段结构

```java
mockMvc.perform(get("/api/books"))        // 发什么请求
        .andExpect(status().isOk())        // 期望什么状态码
        .andExpect(jsonPath("$.length()").value(2));  // 期望什么响应体
```

`perform` 发起一个模拟请求。它不经过网络，也不需要启动 Tomcat，但会走完 Spring MVC 内部的完整流程，所以地址写错、状态码不对都能被发现。

`get`、`post`、`delete` 这些静态方法用来构造不同的请求。POST 需要额外指定内容类型和请求体：

```java
post("/api/books")
    .contentType(MediaType.APPLICATION_JSON)
    .content("{\"title\":\"数据库入门\",\"author\":\"赵六\"}")
```

请求体里的引号需要用反斜杠转义，因为它嵌在 Java 字符串里。

### jsonPath 怎么读

`jsonPath` 用一个表达式定位 JSON 里的位置，`$` 代表整个响应体：

| 表达式 | 含义 |
| --- | --- |
| `$.id` | 顶层的 id 字段 |
| `$.length()` | 数组长度 |
| `$[0].title` | 数组第一个元素的 title |
| `$.fieldErrors.title` | 嵌套对象里的字段 |

还有一个特殊断言：

```java
.andExpect(jsonPath("$.fieldErrors").doesNotExist());
```

它验证 404 响应里没有 `fieldErrors` 字段，也就是第 13 步 `@JsonInclude(NON_NULL)` 真的生效了。这类"某个字段不该出现"的规则，手工看响应很容易忽略。

### 为什么这个测试能测到 400 和 404

`@WebMvcTest` 虽然只加载了一个 Controller，但它会加载所有 `@RestControllerAdvice`。所以第 13 步写的 `GlobalExceptionHandler` 在这个测试里是生效的。

两条错误路径因此都能覆盖：

```text
校验失败（400）
请求体 title 是空格
      ↓
@Valid 检查不通过，抛 MethodArgumentNotValidException
      ↓
GlobalExceptionHandler 转成 ApiError
      ↓
断言状态码 400 和 fieldErrors.title
      ↓
verify(never()) 确认 bookService.create 一次都没被调用

编号不存在（404）
替身按设定抛出 BookNotFoundException
      ↓
GlobalExceptionHandler 转成 ApiError
      ↓
断言状态码 404、message 内容、fieldErrors 不存在
```

`createReturns400AndSkipsServiceWhenTitleIsBlank` 里那句 `verify(bookService, never())` 值得注意。它把第 13 步那个结论固定成了测试：校验失败时 Controller 方法体不执行。以后如果有人把 `@Valid` 删掉，这个用例会失败。

最后一个用例 `pathVariableThatIsNotANumberReturns400` 覆盖的是路径参数类型不对的情况，它由 Spring 内置处理器返回 400，同样不会进入 Service。

## 7. 已有的 contextLoads 是什么

第一节生成的这个测试一直存在：

```java
@SpringBootTest
class BookApiApplicationTests {

    @Test
    void contextLoads() {
    }
}
```

方法体是空的，看起来什么都没测，其实它测的是"整个应用能不能启动成功"。

`@SpringBootTest` 会启动完整容器，所有 Bean 都要创建成功。如果某个类少了注解、两个 Bean 循环依赖、配置文件写错，这个测试就会失败。

它和前面三个测试是互补关系：

```text
BookServiceTest        业务判断对不对
BookRepositoryTest     数据库映射对不对
BookControllerTest     HTTP 契约对不对
BookApiApplicationTests  所有零件能不能装到一起
```

保留它，不需要修改。

## 8. 让测试输出可读

在 `src/test/resources` 下新建 `logback-test.xml`：

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!-- 只在自动化测试时生效，用于把测试输出压到 INFO 级别，方便看清测试结果 -->
<configuration>
    <appender name="CONSOLE" class="ch.qos.logback.core.ConsoleAppender">
        <encoder>
            <pattern>%d{HH:mm:ss.SSS} %-5level %logger{36} - %msg%n</pattern>
        </encoder>
    </appender>

    <root level="INFO">
        <appender-ref ref="CONSOLE"/>
    </root>
</configuration>
```

### 这个文件的作用和生效方式

- 作用：控制测试期间的日志级别和格式。
- 谁读取它：日志框架 Logback 启动时自动在 classpath 根目录查找 `logback-test.xml`，找到就使用。项目里没有任何代码引用这个文件名。
- 什么时候生效：只在测试时。因为它放在 `src/test/resources`，不会被打进最终的 jar。
- 去掉会怎样：`mvn test` 的输出会从 149 行涨到 700 行以上，多出来的都是 Spring 测试框架的 DEBUG 日志，真正的测试结果被埋在里面。

多出那些 DEBUG 日志是有原因的：测试类启动 Spring 之前，Spring Boot 的日志配置还没生效，而 Logback 在没有配置文件时默认输出 DEBUG 级别。加上这个文件就等于提前把级别定下来。

`%logger{36}` 表示日志来源最多显示 36 个字符，超出部分会缩写成 `o.s.b.t.a` 这种形式，行宽更整齐。

## 9. 运行测试

在项目根目录执行：

```bash
mvn test
```

预期输出的关键部分：

```text
[INFO] Running com.example.bookapi.repository.BookRepositoryTest
[INFO] Tests run: 4, Failures: 0, Errors: 0, Skipped: 0
[INFO] Running com.example.bookapi.BookApiApplicationTests
[INFO] Tests run: 1, Failures: 0, Errors: 0, Skipped: 0
[INFO] Running com.example.bookapi.controller.BookControllerTest
[INFO] Tests run: 6, Failures: 0, Errors: 0, Skipped: 0
[INFO] Running com.example.bookapi.service.BookServiceTest
[INFO] Tests run: 5, Failures: 0, Errors: 0, Skipped: 0
[INFO] Results:
[INFO] Tests run: 16, Failures: 0, Errors: 0, Skipped: 0
[INFO] BUILD SUCCESS
```

四个数字的含义：

| 名称 | 含义 |
| --- | --- |
| Tests run | 一共执行了多少个用例 |
| Failures | 断言不通过，代码行为和预期不一致 |
| Errors | 抛出了预期之外的异常，通常是测试本身写错或环境问题 |
| Skipped | 被跳过的用例 |

只要 Failures 和 Errors 都是 0，最后就是 `BUILD SUCCESS`。

### 测试类的执行顺序不固定

上面的输出里，`BookRepositoryTest` 排在最前面，不是按文件名顺序。测试类之间的执行顺序由构建工具决定，不保证稳定。

由此得到一条规则：用例之间不能互相依赖。每个用例都要自己准备数据、自己断言，不能假设"另一个用例已经插好数据了"。这也是 `@DataJpaTest` 自动回滚的价值所在。

### 在 IDEA 中运行

- 打开任意测试类，点击类名左侧的绿色三角，选择 Run，运行整个类。
- 点击某个方法左侧的三角，只运行这一个用例。
- 右键 `src/test/java` 目录，选择 Run 'All Tests'，运行全部。
- 运行完成后，左下角的测试面板用绿色和红色标出结果，点击失败项能直接跳到出错的那一行。

### 只运行一个测试类

```bash
mvn test -Dtest=BookServiceTest
```

调试单个问题时这样跑更快。

### 测试不需要先启动应用

这一点容易误会。`mvn test` 会自己按需启动所需组件，不需要 IDEA 里的应用处于运行状态。而且测试使用的是独立数据库，不会动 `data/bookdb` 里手工练习的数据。

## 13. 完整调用链路

### 启动阶段：mvn test 发生了什么

```text
mvn test
      ↓
编译 src/main/java 和 src/test/java
      ↓
测试插件扫描 target/test-classes，找出名字符合 *Test 的类
      ↓
交给 JUnit 5 引擎，逐个类执行
      ↓
每个类按自己的注解决定要不要启动 Spring，以及启动多少
  ├─ 只有 @ExtendWith(MockitoExtension.class) → 不启动 Spring
  ├─ @DataJpaTest   → 启动 JPA 相关组件，并替换数据源
  ├─ @WebMvcTest    → 启动 Web 相关组件
  └─ @SpringBootTest → 启动完整应用
      ↓
执行所有 @Test 方法，统计通过与失败
      ↓
全部通过 → BUILD SUCCESS；有失败 → BUILD FAILURE，构建中断
```

需要注意的是最后一步：测试失败会让构建失败。这意味着以后接入打包和部署流程时，测试是一道自动生效的关卡。

### 三种测试各自的调用链

三种测试的差别在于"链路从哪里开始，在哪里被替身截断"。

单元测试，链路最短：

```text
JUnit 调用 BookServiceTest.findByIdThrowsWhenIdDoesNotExist
      ↓
直接调用 bookService.findById(99L)     ← 真实的 Service 代码
      ↓
Service 内部调用 bookRepository.findById(99L)
      ↓
替身按设定返回 Optional.empty()        ← 链路在这里截断，不碰数据库
      ↓
orElseThrow 抛出 BookNotFoundException
      ↓
assertThatThrownBy 捕获并检查类型和消息
```

Repository 切片测试，链路只有下半段，但下半段是真的：

```text
JUnit 调用 BookRepositoryTest.saveGeneratesId
      ↓
Spring 已注入真实的 Repository 代理对象
      ↓
bookRepository.save(book)
      ↓
SimpleJpaRepository → EntityManager
      ↓
Hibernate 生成 insert 语句
      ↓
临时内存数据库真的执行 SQL 并生成主键
      ↓
断言 id 不为 null
      ↓
方法结束，事务回滚，数据消失
```

Controller 切片测试，链路是上半段：

```text
JUnit 调用 BookControllerTest.findByIdReturns404WhenServiceThrows
      ↓
mockMvc.perform(get("/api/books/99"))
      ↓
不经过网络，直接进入 Spring MVC 内部流程
      ↓
DispatcherServlet 按地址找到 BookController.findById
      ↓
解析路径参数 99，调用 bookService.findById(99L)
      ↓
替身按设定抛出 BookNotFoundException   ← 链路在这里截断，不碰数据库
      ↓
异常冒泡到 DispatcherServlet
      ↓
GlobalExceptionHandler.handleBookNotFound 被回调，返回 ApiError
      ↓
Jackson 序列化，状态码设为 404
      ↓
andExpect 逐条检查状态码和 JSON 字段
```

三段链路拼起来，正好覆盖第 13 步那条真实请求链路的全长。

### 和真实请求链路的对照

| 真实请求经过的环节 | 单元测试 | Repository 切片 | Controller 切片 | 集成测试 |
| --- | --- | --- | --- | --- |
| Tomcat 网络层 | 不涉及 | 不涉及 | 被 MockMvc 替代 | 启动但不发请求 |
| DispatcherServlet 与参数解析 | 不涉及 | 不涉及 | 真实执行 | 启动 |
| 校验与异常处理 | 不涉及 | 不涉及 | 真实执行 | 启动 |
| Controller | 不涉及 | 不涉及 | 真实执行 | 启动 |
| Service | 真实执行 | 不涉及 | 替身 | 启动 |
| Repository 与 Hibernate | 替身 | 真实执行 | 不涉及 | 启动 |
| 数据库 | 不涉及 | 临时内存库 | 不涉及 | 测试内存库 |

看这张表可以得到一条经验：同一个环节不必被多种测试重复覆盖。Controller 层测状态码和 JSON，Service 层测判断逻辑，Repository 层测映射和 SQL，各管一段。

### 本节新增类的引用与调用关系

| 类或文件 | 谁引用它 | 运行期谁调用它 | 触发时机 |
| --- | --- | --- | --- |
| `BookServiceTest` | 没有任何代码引用 | JUnit 5 引擎 | 执行 `mvn test` 或在 IDEA 中运行 |
| `BookRepositoryTest` | 没有任何代码引用 | JUnit 5 引擎，运行前先由 Spring 启动 JPA 切片 | 同上 |
| `BookControllerTest` | 没有任何代码引用 | JUnit 5 引擎，运行前先由 Spring 启动 Web 切片 | 同上 |
| `logback-test.xml` | 没有任何代码引用 | Logback 初始化时按文件名查找 | 测试进程启动时 |

四个新增文件有一个共同点：都不被任何代码引用，全部靠约定被发现。测试类靠命名约定和注解被扫描，日志配置靠固定文件名被加载。这类"按约定生效"的写法在框架里很常见，判断依据是文件位置和名字，而不是搜索引用。

反过来，被测的三个类没有任何变化，也不知道测试的存在。依赖方向始终是测试指向业务代码，不能反过来。

- 能解释 `@DataJpaTest` 里为什么可以断言数据库是空的。

## 常见问题

### 提示找不到 org.junit.jupiter

确认 `pom.xml` 里有 `spring-boot-starter-test`，并且测试类放在 `src/test/java` 下。放在 `src/main/java` 里会因为 `scope=test` 而找不到这些类。

### 测试类里 @Mock 标记的字段是 null

检查类上是否写了 `@ExtendWith(MockitoExtension.class)`。少了这一行，Mockito 不会介入，字段不会被赋值。

### mvn test 显示 No tests to run

检查类名是否以 `Test` 结尾，方法上是否有 `@Test`。注意 `@Test` 要导入 `org.junit.jupiter.api.Test`，不是 JUnit 4 的 `org.junit.Test`。

### BookControllerTest 启动失败，提示缺少 BookService

`@WebMvcTest` 不会创建 Service。必须用 `@MockBean` 提供一个替身放进容器。

### 断言 fieldErrors 顺序时失败

不要断言多个字段的先后顺序，只断言具体字段的值，例如 `jsonPath("$.fieldErrors.title")`。原因见第 13 步。

### UnnecessaryStubbingException

`when(...)` 设定了返回值，但被测代码根本没调用那个方法。多数情况说明设定写多了，或者参数没对上。删掉用不到的设定即可。

### 断言数据库为空的用例失败

确认使用的是 `@DataJpaTest`，不是 `@SpringBootTest`。后者会启动完整应用，`DataInitializer` 会插入三本初始图书。

### 测试时报 Database may be already in use

`@DataJpaTest` 会替换数据源，一般不会出现这个问题。如果换成 `@SpringBootTest` 并且 IDEA 里的应用正在运行，需要确认 `src/test/resources/application.properties` 里用的是内存数据库，不是 `data/bookdb` 文件。

### 测试通过但接口实际有问题

切片测试用替身替换了下层，所以它证明不了整条链路。这类问题要靠集成测试或手工验证补充。本节的做法是三层各测一段，再保留一个启动测试，代价和收益比较平衡。
