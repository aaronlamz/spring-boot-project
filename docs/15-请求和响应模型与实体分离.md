# 第 15 步：请求和响应模型与实体分离

## 这一节要完成什么

到上一节为止，`Book` 这一个类同时承担了三件事：

```text
Book
 ├─ @Entity、@Table、@Id      → 描述数据库表结构
 ├─ Jackson 读取它的 getter    → 决定接口返回什么 JSON
 └─ @NotBlank                 → 决定客户端能提交什么
```

只有一个类时这样写最省事，但它带来四个具体问题。

第一，客户端可以在请求体里提交 id。上一节靠 Service 里的 `book.setId(null)` 兜住，属于事后补救。

第二，实体加字段会自动出现在接口响应里。假设以后给图书加上进货价、库存或录入人，这些字段会立刻暴露给所有调用方，而且不会有任何提示。

第三，数据库结构和接口契约被绑死。数据库把 `title` 改成 `book_title`，接口返回的字段名也跟着变，所有调用方都要改。

第四，同一个类上堆着两套注解，一套给数据库，一套给校验，职责不清。

本节把接口的输入和输出各自独立成类：

```text
客户端 JSON
      ↓
BookRequest    只包含允许提交的字段     ← 本节新增
      ↓
BookMapper     负责三种模型之间的转换   ← 本节新增
      ↓
Book           只负责数据库映射
      ↓
BookMapper
      ↓
BookResponse   只包含允许返回的字段     ← 本节新增
      ↓
返回给客户端的 JSON
```

完成后接口的 JSON 结构和状态码完全不变，调用方感觉不到差别，但内部结构更安全。这一节也是第一次体会到有测试的好处：改完立刻能确认没有改坏任何行为。

## 1. 三个新类的分工

| 类 | 负责什么 | 包含哪些字段 |
| --- | --- | --- |
| `BookRequest` | 客户端能提交什么 | title、author |
| `Book` | 数据库表结构 | id、title、author |
| `BookResponse` | 接口返回什么 | id、title、author |

现在三者字段几乎一样，看起来是重复劳动。它们的价值在于以后各自独立变化：

```text
数据库要加成本价    → 只改 Book，接口不受影响
接口要少返回作者    → 只改 BookResponse，数据库不受影响
客户端要提交出版社  → 只改 BookRequest，其余不受影响
```

一个类承担三种职责时，上面任何一种变化都会牵动另外两边。

## 2. 创建 BookRequest

在 IDEA 中：

1. 右键 `com.example.bookapi`。
2. 选择 **New → Package**，输入 `dto`。
3. 右键 `dto` 包，选择 **New → Java Class**，输入 `BookRequest`。

完整代码：

```java
package com.example.bookapi.dto;

import javax.validation.constraints.NotBlank;

/**
 * 新增和修改图书时，客户端允许提交的字段。
 */
public class BookRequest {

    @NotBlank(message = "书名不能为空")
    private String title;

    @NotBlank(message = "作者不能为空")
    private String author;

    public String getTitle() {
        return title;
    }

    public void setTitle(String title) {
        this.title = title;
    }

    public String getAuthor() {
        return author;
    }

    public void setAuthor(String author) {
        this.author = author;
    }
}
```

### dto 是什么意思

DTO 是 Data Transfer Object 的缩写，意思是“用于传输数据的对象”。它只装数据，不含业务逻辑，专门用在两层之间传递信息。

包名用 `dto` 是一种常见约定。看到这个包名，就知道里面的类是接口的输入输出模型，不是数据库实体。

### 这个类的作用和调用关系

- 作用：定义客户端在 POST 和 PUT 请求体里允许提交的字段，并在这里做校验。
- 编译期引用：`BookController` 的方法参数引用它，`BookMapper` 读取它。它自己不引用任何项目内的类。
- 对象从哪来：由 Jackson 创建。项目代码里没有 `new BookRequest()`。
- 运行期触发：请求到达时，`@RequestBody` 让 Jackson 把 JSON 转成这个对象，`@Valid` 随后检查它的注解。
- 去掉会怎样：Controller 只能重新接收实体，客户端又可以提交 id，本节的四个问题全部回来。

### 为什么没有 id 字段

这是本节最重要的一处设计。

新增图书时 id 由数据库生成，修改图书时 id 来自 URL 路径，两种情况都不需要客户端提交 id。类里没有这个字段，客户端就没有任何办法把 id 传进业务代码，问题从根上消失了。

对比一下上一节的做法：字段存在，靠 Service 执行 `book.setId(null)` 清掉。那是发现问题后补救，现在是让问题无法发生。

### 为什么需要 setter

Jackson 从 JSON 创建对象的过程分两步：

```text
先用无参构造方法 new 一个空对象
      ↓
再按 JSON 的字段名调用对应的 setter 填值
```

所以请求模型必须有 setter，也必须有无参构造方法。这里没有显式写构造方法，Java 会自动提供一个默认的无参构造方法，条件是类里没有写任何其他构造方法。

### 校验注解从实体搬到了这里

`@NotBlank` 原来在 `Book` 上，现在移到 `BookRequest`。原因是校验属于入口检查，应该发生在接收外部数据的地方。

`message` 内容保持不变，所以第 13 步验证过的那些 400 响应结构完全一样。

## 3. 创建 BookResponse

在 `dto` 包中新建 `BookResponse`：

```java
package com.example.bookapi.dto;

/**
 * 接口返回给客户端的图书字段。
 */
public class BookResponse {

    private Long id;
    private String title;
    private String author;

    public BookResponse(Long id, String title, String author) {
        this.id = id;
        this.title = title;
        this.author = author;
    }

    public Long getId() {
        return id;
    }

    public String getTitle() {
        return title;
    }

    public String getAuthor() {
        return author;
    }
}
```

### 这个类的作用和调用关系

- 作用：定义接口返回给客户端的字段。
- 编译期引用：`BookController` 的返回类型引用它，`BookMapper` 创建它。
- 对象从哪来：由 `BookMapper` 用 `new` 创建。
- 运行期触发：Controller 方法返回后，Jackson 调用它的 getter 生成 JSON。
- 去掉会怎样：Controller 只能直接返回实体，实体新增的任何字段都会自动出现在响应里。

### 为什么只有构造方法和 getter

和请求模型正好相反：

| | `BookRequest` | `BookResponse` |
| --- | --- | --- |
| 数据从哪来 | 客户端的 JSON | 程序内部的实体 |
| 谁创建对象 | Jackson | 我们的代码 |
| 需要 setter 吗 | 需要，Jackson 靠它填值 | 不需要，构造时一次填好 |
| 需要 getter 吗 | 需要，转换时读取 | 需要，Jackson 靠它生成 JSON |

这和第 13 步的 `ApiError` 是同一种写法：由我们创建、由 Jackson 读取的类，只提供构造方法和 getter。少一个 setter 就少一处被意外修改的可能。

### 这里的 id 为什么可以有

响应里必须带 id，否则客户端新增图书后不知道编号是多少，也没法再去修改或删除它。

方向不同，允许的字段就不同。这正是把输入和输出分成两个类的好处：一个类只回答一个问题。

## 4. 创建 BookMapper

在 `dto` 包中新建 `BookMapper`：

```java
package com.example.bookapi.dto;

import com.example.bookapi.model.Book;
import org.springframework.stereotype.Component;

import java.util.ArrayList;
import java.util.List;

/**
 * 负责请求模型、实体和响应模型之间的转换。
 */
@Component
public class BookMapper {

    public Book toEntity(BookRequest request) {
        Book book = new Book();
        book.setTitle(request.getTitle());
        book.setAuthor(request.getAuthor());
        return book;
    }

    public BookResponse toResponse(Book book) {
        return new BookResponse(book.getId(), book.getTitle(), book.getAuthor());
    }

    public List<BookResponse> toResponseList(List<Book> books) {
        List<BookResponse> responses = new ArrayList<>();
        for (Book book : books) {
            responses.add(toResponse(book));
        }
        return responses;
    }
}
```

### 这个类的作用和调用关系

- 作用：集中处理三种模型之间的字段搬运，避免转换代码散落在各个 Controller 方法里。
- 编译期引用：`BookController` 引用它。它引用 `BookRequest`、`BookResponse` 和 `Book`。
- 对象从哪来：由 Spring 创建。`@Component` 让它进入容器，`BookController` 通过构造器注入拿到它。
- 运行期触发：`BookController` 的方法直接调用它，属于普通的方法调用，不是框架回调。
- 去掉会怎样：转换代码要写进每个 Controller 方法，重复且容易漏字段。

### 三个方法分别做什么

| 方法 | 输入 | 输出 | 用在哪 |
| --- | --- | --- | --- |
| `toEntity` | `BookRequest` | `Book` | POST 和 PUT，把客户端数据交给业务层 |
| `toResponse` | `Book` | `BookResponse` | 返回单本图书 |
| `toResponseList` | `List<Book>` | `List<BookResponse>` | 返回图书列表 |

### toEntity 为什么不设置 id

```java
Book book = new Book();
book.setTitle(request.getTitle());
book.setAuthor(request.getAuthor());
```

只搬两个字段。`Book` 的 id 保持默认值 `null`，正好表示“这是一个还没有编号的对象”。

新增时，数据库会生成编号。修改时，Service 会先按 URL 里的 id 查出已存在的图书，再把这两个字段覆盖进去，所以这里的 id 是不是 `null` 并不影响修改流程。

### toResponseList 里的循环

```java
List<BookResponse> responses = new ArrayList<>();
for (Book book : books) {
    responses.add(toResponse(book));
}
return responses;
```

逐个转换再放进新集合。`for (Book book : books)` 是增强 for 循环，含义是“把 books 里的每个元素依次赋给 book”。

注意它复用了 `toResponse`，而不是把三行赋值再抄一遍。以后响应模型增加字段，只需要改 `toResponse` 一处。

### 为什么方法不写成 static

写成静态方法也能工作，本节选择做成 Spring 组件，有两个原因。

一是保持和项目其他部分一致。`BookController`、`BookService`、`BookRepository` 都由容器管理，通过构造器注入获得，转换器也这样处理，读代码时不需要切换思路。

二是留出扩展空间。以后转换逻辑可能需要用到别的组件，例如查配置、查字典表、按语言返回不同文案。到那时如果它是静态方法，就得先改成实例方法再改所有调用处。

第 13 步的 `ApiError` 用 `new` 创建，这里的 `BookMapper` 用注入，区别还是那条判断：装数据的对象自己 `new`，干活的对象交给容器。


### 实体上不再有校验，会不会漏掉检查

不会。校验发生在请求进入 Controller 之前，由 `BookRequest` 上的注解负责。所有走接口的数据都会被检查。

## 6. 修改 BookController

完整代码：

```java
package com.example.bookapi.controller;

import com.example.bookapi.dto.BookMapper;
import com.example.bookapi.dto.BookRequest;
import com.example.bookapi.dto.BookResponse;
import com.example.bookapi.service.BookService;
import org.springframework.http.HttpStatus;
import org.springframework.web.bind.annotation.DeleteMapping;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.PutMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.ResponseStatus;
import org.springframework.web.bind.annotation.RestController;

import javax.validation.Valid;
import java.util.List;

@RestController
@RequestMapping("/api/books")
public class BookController {

    private final BookService bookService;
    private final BookMapper bookMapper;

    public BookController(BookService bookService, BookMapper bookMapper) {
        this.bookService = bookService;
        this.bookMapper = bookMapper;
    }

    @GetMapping
    public List<BookResponse> findAll() {
        return bookMapper.toResponseList(bookService.findAll());
    }

    @PostMapping
    @ResponseStatus(HttpStatus.CREATED)
    public BookResponse create(@Valid @RequestBody BookRequest request) {
        return bookMapper.toResponse(bookService.create(bookMapper.toEntity(request)));
    }

    @PutMapping("/{id}")
    public BookResponse update(@PathVariable Long id, @Valid @RequestBody BookRequest request) {
        return bookMapper.toResponse(bookService.update(id, bookMapper.toEntity(request)));
    }

    @DeleteMapping("/{id}")
    @ResponseStatus(HttpStatus.NO_CONTENT)
    public void delete(@PathVariable Long id) {
        bookService.delete(id);
    }

    @GetMapping("/{id}")
    public BookResponse findById(@PathVariable Long id) {
        return bookMapper.toResponse(bookService.findById(id));
    }
}
```

### 构造方法多了一个参数

```java
public BookController(BookService bookService, BookMapper bookMapper) {
```

Spring 创建 `BookController` 时，会按参数类型从容器里找对应的 Bean，一次注入两个。构造器注入的写法和第 11 步一样，只是参数变多。

参数越多说明这个类依赖越多。目前两个属于正常范围，如果以后涨到五六个，就该考虑这个类是不是承担了太多职责。

### 方法签名的变化

```java
// 上一节
public Book create(@Valid @RequestBody Book book)

// 本节
public BookResponse create(@Valid @RequestBody BookRequest request)
```

参数和返回值都换成了 DTO。从这一刻起，实体类不再出现在接口签名上，Controller 成了实体和外部世界之间的边界。

### 一行里的三步

```java
return bookMapper.toResponse(bookService.create(bookMapper.toEntity(request)));
```

这一行嵌套了三次调用，从最里面往外读：

```text
bookMapper.toEntity(request)   把请求模型转成实体
      ↓
bookService.create(...)        交给业务层，返回带 id 的实体
      ↓
bookMapper.toResponse(...)     把实体转成响应模型
```

写成三行也完全可以，效果一样：

```java
Book book = bookMapper.toEntity(request);
Book saved = bookService.create(book);
return bookMapper.toResponse(saved);
```

嵌套写法更短，分行写法更容易打断点调试。刚开始建议按分行的方式理解这段代码。

### 转换为什么放在 Controller

因为 DTO 描述的是接口契约，而 Controller 正是负责接口的那一层。

由此可以确定各层看到的对象类型：

| 层 | 处理的对象 |
| --- | --- |
| Controller | DTO 进，DTO 出，中间转成实体调用 Service |
| Service | 只处理实体，完全不知道 DTO 的存在 |
| Repository | 只处理实体 |

好处是接口层的变化不会传导到业务层。以后接口要改字段名、加版本、返回不同结构，只需要动 DTO 和 Controller。

## 7. Service 和 Repository 没有任何改动

这一节没有修改 `BookService` 和 `BookRepository`，一行都没改。

原因是它们从一开始就只依赖实体。Controller 把 DTO 转成实体之后再往下调用，下层察觉不到上层换了模型。

`BookService.create` 里的 `book.setId(null)` 也保留着。走接口进来的请求已经不可能带 id，这行现在是一层额外保险，成本只有一行代码，可以留着防止以后有别的调用方直接使用 Service。

## 8. 更新 Controller 测试

`BookControllerTest` 需要两处调整。

第一处，类上增加一个注解：

```java
@WebMvcTest(BookController.class)
@Import(BookMapper.class)
class BookControllerTest {
```

原因是第 14 步讲过的：`@WebMvcTest` 只加载 Web 层组件，`@Component` 标注的类不在其中。`BookMapper` 是 `@Component`，不导入的话容器里没有它，`BookController` 的构造方法就少一个参数，测试会在启动阶段直接失败，报错信息大意是找不到 `BookMapper` 类型的 Bean。

这里也可以像 `BookService` 那样用 `@MockBean` 造一个替身，但没必要。转换器没有外部依赖，逻辑简单且确定，用真实的更能验证字段有没有搬对。

选择替身还是真实对象，可以按这个标准判断：

| 依赖的特点 | 建议 |
| --- | --- |
| 要访问数据库、网络等外部资源 | 用替身 |
| 需要制造特定场景，例如抛异常 | 用替身 |
| 纯粹的内存计算，没有外部依赖 | 用真实对象 |

第二处，新增一个用例，验证请求体里的 id 会被忽略：

```java
@Test
void createIgnoresIdInRequestBody() throws Exception {
    given(bookService.create(any(Book.class)))
            .willReturn(new Book(4L, "数据库入门", "赵六"));

    mockMvc.perform(post("/api/books")
                    .contentType(MediaType.APPLICATION_JSON)
                    .content("{\"id\":123,\"title\":\"数据库入门\",\"author\":\"赵六\"}"))
            .andExpect(status().isCreated())
            .andExpect(jsonPath("$.id").value(4));

    ArgumentCaptor<Book> sentToService = ArgumentCaptor.forClass(Book.class);
    verify(bookService).create(sentToService.capture());
    assertThat(sentToService.getValue().getId()).isNull();
}
```

它检查三件事：请求带着 `"id":123` 也返回 201；响应里的 id 是数据库给的 4，不是 123；真正交给 Service 的那个实体，id 是 `null`。

最后那两行用到了第 14 步的 `ArgumentCaptor`，作用还是把实际传入的参数抓下来检查。

其余用例完全不用改。这一点值得注意：测试断言的是 HTTP 行为和 JSON 字段，而这两样在本次重构中没有变化。测试稳定说明它们盯的是对外契约，不是内部实现。

## 9. 新增 BookMapper 的测试

新建：

```text
src/test/java/com/example/bookapi/dto/BookMapperTest.java
```

完整代码：

```java
package com.example.bookapi.dto;

import com.example.bookapi.model.Book;
import org.junit.jupiter.api.Test;

import java.util.Arrays;
import java.util.Collections;
import java.util.List;

import static org.assertj.core.api.Assertions.assertThat;

class BookMapperTest {

    private final BookMapper bookMapper = new BookMapper();

    @Test
    void toEntityCopiesTitleAndAuthorButLeavesIdNull() {
        BookRequest request = new BookRequest();
        request.setTitle("数据库入门");
        request.setAuthor("赵六");

        Book book = bookMapper.toEntity(request);

        assertThat(book.getId()).isNull();
        assertThat(book.getTitle()).isEqualTo("数据库入门");
        assertThat(book.getAuthor()).isEqualTo("赵六");
    }

    @Test
    void toResponseCopiesAllThreeFields() {
        BookResponse response = bookMapper.toResponse(new Book(1L, "Spring Boot 入门", "张三"));

        assertThat(response.getId()).isEqualTo(1L);
        assertThat(response.getTitle()).isEqualTo("Spring Boot 入门");
        assertThat(response.getAuthor()).isEqualTo("张三");
    }

    @Test
    void toResponseListKeepsOrder() {
        List<Book> books = Arrays.asList(
                new Book(1L, "Spring Boot 入门", "张三"),
                new Book(2L, "Java 核心技术", "李四"));

        List<BookResponse> responses = bookMapper.toResponseList(books);

        assertThat(responses).hasSize(2);
        assertThat(responses.get(0).getTitle()).isEqualTo("Spring Boot 入门");
        assertThat(responses.get(1).getTitle()).isEqualTo("Java 核心技术");
    }

    @Test
    void toResponseListReturnsEmptyListForEmptyInput() {
        List<BookResponse> responses = bookMapper.toResponseList(Collections.<Book>emptyList());

        assertThat(responses).isEmpty();
    }
}
```

### 这里为什么直接 new

```java
private final BookMapper bookMapper = new BookMapper();
```

转换器没有任何依赖，测试里直接创建就行，不需要启动 Spring，也不需要 Mockito。这是四个测试类里最快的一个，四个用例总共几十毫秒。

`@Component` 只影响运行时由谁创建它，不影响这个类能不能被 `new`。

### 字段搬运也值得测

转换代码看起来不容易出错，实际很容易写错。最典型的是复制粘贴时把字段顺序搞乱：

```java
// 错误示范
return new BookResponse(book.getId(), book.getAuthor(), book.getTitle());
```

编译能通过，因为两个参数都是 `String`，但书名和作者会互换。`toResponseCopiesAllThreeFields` 这个用例能立刻发现这种问题。

最后那个用例检查空列表返回空列表，而不是 `null`。返回 `null` 会让调用方多写判断，也会让接口返回 `null` 而不是 `[]`。

## 12. 验证客户端传的 id 被忽略

这是本节唯一一处行为差异，值得单独验证：

```bash
curl -i -X POST http://localhost:8080/api/books -H 'Content-Type: application/json' -d '{"id":123,"title":"多余字段测试","author":"钱七"}'
```

实际返回：

```text
HTTP/1.1 201
{"id":5,"title":"多余字段测试","author":"钱七"}
```

请求里写的是 123，数据库生成的是 5。id 在进入程序的第一步就被丢掉了，因为 `BookRequest` 里根本没有这个字段。

### 多传字段为什么不报错

Spring Boot 默认让 Jackson 忽略 JSON 里多出来的字段。所以上面这个请求不会返回 400，`id` 被静默丢弃。

两种做法各有取舍：

| 策略 | 好处 | 代价 |
| --- | --- | --- |
| 忽略未知字段（当前默认） | 客户端多传字段不会导致失败，接口更宽容 | 字段名拼错时不会有任何提示 |
| 未知字段直接报错 | 拼错字段名立刻暴露 | 客户端升级时容易被旧字段卡住 |

需要改成严格模式时，可以在 `application.properties` 里加一行：

```properties
spring.jackson.deserialization.fail-on-unknown-properties=true
```

本课程保持默认的宽容策略。这里的重点是知道默认行为是什么，以及它带来的后果，而不是马上去改配置。

## 15. 完整调用链路

### 启动阶段新增了什么

```text
... 扫描 com.example.bookapi 及子包
      ↓
除了 Controller、Service、DataInitializer、GlobalExceptionHandler
还扫描到 BookMapper(@Component)                       ← 本节新增
      ↓
创建单例 Bean 时，BookController 的构造方法需要两个参数
  ├─ BookService
  └─ BookMapper                                       ← 本节新增
      ↓
校验器不再关心 Book，改为在校验 BookRequest 时使用
      ↓
... 其余与上一节相同
```

`BookRequest` 和 `BookResponse` 不是 Bean，启动阶段不会创建它们。它们在每次请求时才产生对象，用完就丢。

### 请求阶段：一次 POST 的完整链路

```text
curl 发出 POST /api/books，请求体带 title 和 author
      ↓
Tomcat → DispatcherServlet 找到 BookController.create
      ↓
@RequestBody：Jackson 创建 BookRequest 对象
  ├─ 先调用无参构造方法
  ├─ 再调用 setTitle、setAuthor
  └─ JSON 里多出来的字段被忽略，例如 id
      ↓
@Valid：Hibernate Validator 检查 BookRequest 上的 @NotBlank
      ↓
   校验失败 → MethodArgumentNotValidException → 400，与第 13 步相同
      ↓ 校验通过
执行 create 方法体
      ↓
bookMapper.toEntity(request)：new Book()，搬入 title 和 author，id 保持 null
      ↓
bookService.create(book)：执行 setId(null)，调用 Repository
      ↓
Hibernate 生成 insert，H2 生成主键并写回 Book.id
      ↓
bookMapper.toResponse(book)：new BookResponse(id, title, author)
      ↓
Controller 返回 BookResponse
      ↓
Jackson 调用它的三个 getter，生成 JSON
      ↓
@ResponseStatus(CREATED) → 201，Tomcat 返回响应
```

和上一节相比，多出来的只有两处转换，其余环节完全没变。这也是接口行为保持一致的原因。

### 对象在链路上的形态变化

同一份数据在一次请求里换了三次形态：

```text
JSON 文本            {"title":"数据库入门","author":"赵六"}
      ↓ Jackson
BookRequest 对象     title、author
      ↓ BookMapper.toEntity
Book 对象            id=null、title、author
      ↓ 数据库插入后
Book 对象            id=4、title、author
      ↓ BookMapper.toResponse
BookResponse 对象    id=4、title、author
      ↓ Jackson
JSON 文本            {"id":4,"title":"数据库入门","author":"赵六"}
```

看这张图可以明确每种类型的活动范围：

| 类型 | 出现在哪些位置 |
| --- | --- |
| `BookRequest` | 只在 Controller 方法参数上，不往下传 |
| `Book` | Controller 内部、Service、Repository、数据库 |
| `BookResponse` | 只在 Controller 返回值上，不往下传 |

DTO 停在 Controller，实体不出 Controller，这是本节确立的边界。

### 本节新增类的引用与调用关系

| 类 | 谁引用它 | 运行期谁调用它 | 触发时机 |
| --- | --- | --- | --- |
| `BookRequest` | `BookController` 的参数、`BookMapper` | Jackson 调用 setter，`BookMapper` 调用 getter | 请求体解析和转换时 |
| `BookResponse` | `BookController` 的返回值、`BookMapper` | `BookMapper` 调用构造方法，Jackson 调用 getter | 转换和序列化响应时 |
| `BookMapper` | `BookController` | `BookController` 的方法直接调用 | 每次处理请求时 |

和前几节的框架回调类不同，`BookMapper` 是被我们自己的代码显式调用的。三类写法现在都出现过了：

| 类型 | 例子 | 谁调用它的方法 |
| --- | --- | --- |
| 业务组件 | `BookService`、`BookMapper` | 我们的代码 |
| 框架回调组件 | `DataInitializer`、`GlobalExceptionHandler` | 框架 |
| 数据模型 | `Book`、`BookRequest`、`BookResponse`、`ApiError` | 框架或转换代码读写它的字段 |

判断一个新类属于哪一类，就能推断出它的对象由谁创建、方法由谁调用。

## 常见问题

### 启动时报找不到 BookMapper 类型的 Bean

确认 `BookMapper` 上有 `@Component`，并且类在 `com.example.bookapi.dto` 包下，能被扫描到。

### Controller 测试启动失败，提示缺少 BookMapper

`@WebMvcTest` 不加载 `@Component`。在测试类上补一行：

```java
@Import(BookMapper.class)
```

### 校验不生效，空书名也能保存

确认 `@NotBlank` 已经写在 `BookRequest` 上，并且 Controller 的参数类型是 `BookRequest` 且带 `@Valid`。只把注解留在实体上是不会生效的，因为实体已经不再是请求参数。

### 响应里出现了不该有的字段

检查 `BookResponse` 里是否真的声明了这个字段。如果响应长得和实体一样，可能是 Controller 还在直接返回 `Book`。

### 响应里缺少 id

确认 `BookResponse` 的构造方法第一个参数传的是 `book.getId()`，并且这个 `Book` 是 Service 返回的那个对象，不是转换前的那个。

### 书名和作者的内容对调了

检查 `toResponse` 里参数顺序。两个字段都是 `String`，写错顺序编译不会报错。`BookMapperTest` 里的 `toResponseCopiesAllThreeFields` 就是为了拦住这种问题。

### 请求里多传字段没有报错

这是 Spring Boot 的默认行为，未知字段会被忽略，见第 12 步的说明。

### 返回列表时报空指针

确认 `toResponseList` 里先 `new ArrayList<>()` 再往里加元素，并且在列表为空时返回空集合而不是 `null`。
