# 第 16 步：统一响应结构和业务错误码

## 这一节要完成什么

到上一节为止，接口返回的结构分成好几种：

```text
查询成功   {"id":1,"title":"Spring Boot 入门","author":"张三"}
新增成功   201 加图书 JSON
删除成功   204，没有响应体
参数错误   400 加 {"status":400,"message":...,"fieldErrors":{...}}
编号不存在 404 加 {"status":404,"message":...}
JSON 语法错误  400 加 {"timestamp":...,"status":400,"error":...,"path":...}
```

调用方要写好几套解析逻辑：先看状态码，再判断是哪种响应体，还要处理没有响应体的情况。字段名也不统一，成功时数据在最外层，失败时说明在 `message`，还有一种失败在 `error`。

本节把所有响应统一成同一个结构：

```json
{"code": 0, "msg": "成功", "data": {}}
```

三个字段的含义固定：

| 字段 | 含义 |
| --- | --- |
| `code` | 业务返回码，0 表示成功，非 0 表示失败原因 |
| `msg` | 给人看的说明文字 |
| `data` | 业务数据，失败时通常为 `null` |

完成后，调用方只需要一套解析逻辑：取 `code` 判断成功失败，成功就读 `data`，失败就显示 `msg`。

这一节会改变已有接口的响应结构和状态码，属于本课程第一次主动修改对外契约。第 14 节写的自动化测试会在这时发挥作用：改完跑一遍就知道哪些行为受到影响。

## 1. 两种错误表达风格

在动手之前要先理解这个选择，因为它决定了后面所有接口的样子。

风格一是用 HTTP 状态码表达结果，也就是第 13 节的做法：

```text
成功 200，参数错误 400，资源不存在 404，服务器出错 500
```

风格二是 HTTP 状态码固定 200，用响应体里的 `code` 表达业务结果：

```text
一律 200，成功 code=0，参数错误 code=1001，资源不存在 code=1002
```

两者的取舍：

| | 用 HTTP 状态码 | 用业务码 |
| --- | --- | --- |
| 契约表达 | 借用 HTTP 语义，符合 REST 习惯 | 自己定义，表达能力更细，可以有几百个码 |
| 调用方处理 | 要同时看状态码和响应体 | 只看响应体一个字段 |
| 网关和监控 | 直接按状态码统计错误率 | 状态码全是 200，需要额外解析响应体 |
| 前端处理 | 需要区分网络错误和业务错误 | 业务错误都在同一个分支里 |
| 排查问题 | 抓包时一眼看出失败 | 必须看响应体才知道是否失败 |

没有绝对的对错。本课程后面统一采用第二种风格，因为国内很多团队的服务端接口是这样约定的，前端也按这个约定封装请求。先把这种风格写熟，遇到第一种风格时反过来理解也很容易。

必须知道它的代价：所有失败都返回 200，网关、负载均衡和监控系统看不出错误。采用这种风格的团队通常要额外做两件事，一是在日志和监控里按 `code` 统计失败率，二是保留服务器真正不可用时的 5xx，例如应用没启动、连接被拒绝，这些不是业务代码能控制的。

## 2. 创建 ErrorCode 枚举

在 IDEA 中：

1. 右键 `com.example.bookapi`，选择 **New → Package**，输入 `common`。
2. 右键 `common` 包，选择 **New → Java Class**。
3. 在弹出的类型里选择 **Enum**，输入 `ErrorCode`。

完整代码：

```java
package com.example.bookapi.common;

/**
 * 业务返回码。0 表示成功，其余表示各种失败原因。
 */
public enum ErrorCode {

    SUCCESS(0, "成功"),
    PARAM_INVALID(1001, "请求参数不正确"),
    BOOK_NOT_FOUND(1002, "图书不存在"),
    SERVER_ERROR(9999, "服务器内部错误");

    private final int code;
    private final String message;

    ErrorCode(int code, String message) {
        this.code = code;
        this.message = message;
    }

    public int getCode() {
        return code;
    }

    public String getMessage() {
        return message;
    }
}
```

### enum 是什么

`enum` 用于定义一组固定不变的取值。这里的四个名字就是这个类型的全部可能值，不能再有第五个，除非改代码。

和普通类相比，枚举有两个特点：取值有限且可穷举，每个取值都是单例，程序运行期间只有一个 `ErrorCode.SUCCESS` 对象。

### 枚举可以带字段

```java
SUCCESS(0, "成功"),
```

这一行相当于用 `(0, "成功")` 这两个参数创建了名为 `SUCCESS` 的那个唯一对象。参数会传给下面的构造方法：

```java
ErrorCode(int code, String message) {
    this.code = code;
    this.message = message;
}
```

枚举的构造方法不能写 `public`，因为只允许枚举自己在声明取值时调用它，外部代码没有办法再创建新的取值。

注意最后一个取值 `SERVER_ERROR(9999, "服务器内部错误");` 后面是分号，前面几个用逗号分隔。这是枚举的固定写法。

### 为什么不直接写数字和文字

不用枚举也能工作：

```java
// 不推荐
return ApiResponse.fail(1002, "图书不存在");
```

问题是这些数字和文字会散落在各个文件里。同一个错误在两处写成 1002 和 1020，或者文案一处叫“图书不存在”另一处叫“找不到图书”，都不会有任何提示。

用枚举以后，全部返回码集中在一个文件里，重复和冲突一眼能看出来。IDEA 里对着 `ErrorCode.BOOK_NOT_FOUND` 按 `Option + F7`，还能查出哪些地方用了这个码。

### 码值为什么这样分段

本课程的约定很简单：

| 区间 | 用途 |
| --- | --- |
| 0 | 成功 |
| 1001 起 | 业务错误，按模块递增 |
| 9999 | 兜底的服务器错误 |

真实项目通常会按模块划分更大的区间，例如某个模块用 10 万段、另一个模块用 20 万段，好处是看到码值就知道来自哪个服务。现在只有一个模块，先用四位数够了。

关键不是具体怎么分，而是提前定好规则，避免以后随手加码造成冲突。

### 这个枚举的作用和调用关系

- 作用：集中定义所有业务返回码和默认文案。
- 编译期引用：`ApiResponse`、`BusinessException`、`GlobalExceptionHandler` 都引用它。
- 对象从哪来：由 JVM 在类加载时创建，每个取值只有一个实例，不需要也不能 `new`。
- 运行期触发：被上面那些类读取 `getCode()` 和 `getMessage()`。
- 去掉会怎样：返回码变成散落各处的数字，容易冲突且难以统计。

## 3. 创建 ApiResponse

在 `common` 包中新建 `ApiResponse`：

```java
package com.example.bookapi.common;

/**
 * 所有接口统一的返回结构。
 *
 * @param <T> 业务数据的类型
 */
public class ApiResponse<T> {

    private final int code;
    private final String msg;
    private final T data;

    private ApiResponse(int code, String msg, T data) {
        this.code = code;
        this.msg = msg;
        this.data = data;
    }

    public static <T> ApiResponse<T> ok(T data) {
        return new ApiResponse<T>(ErrorCode.SUCCESS.getCode(), ErrorCode.SUCCESS.getMessage(), data);
    }

    public static <T> ApiResponse<T> ok() {
        return ok(null);
    }

    public static <T> ApiResponse<T> fail(ErrorCode errorCode) {
        return new ApiResponse<T>(errorCode.getCode(), errorCode.getMessage(), null);
    }

    public static <T> ApiResponse<T> fail(ErrorCode errorCode, String msg) {
        return new ApiResponse<T>(errorCode.getCode(), msg, null);
    }

    public static <T> ApiResponse<T> fail(ErrorCode errorCode, String msg, T data) {
        return new ApiResponse<T>(errorCode.getCode(), msg, data);
    }

    public int getCode() {
        return code;
    }

    public String getMsg() {
        return msg;
    }

    public T getData() {
        return data;
    }
}
```

### 尖括号里的 T 是什么

```java
public class ApiResponse<T> {
```

`T` 是类型参数，可以理解为“暂时不确定的类型”，等使用时再填。第 12 节的 `JpaRepository<Book, Long>` 用的是同一套机制。

因为 `data` 装什么由接口决定：

```java
ApiResponse<BookResponse>        单本图书
ApiResponse<List<BookResponse>>  图书列表
ApiResponse<Void>                没有数据
```

如果把 `data` 声明成 `Object`，编译器就无法帮忙检查类型，调用方拿到数据后还要自己强制转换。用类型参数可以在编译期就确定 `data` 是什么。

`ApiResponse<Void>` 里的 `Void` 是一个特殊类型，表示“没有值”，只能填 `null`。它和方法上的小写 `void` 不是一回事，小写的用于方法返回类型，大写的可以当类型参数。

### static 方法上的 <T> 又是什么

```java
public static <T> ApiResponse<T> ok(T data) {
```

静态方法不属于任何实例，用不到类上声明的那个 `T`，所以要在方法自己的返回类型前面再声明一次。写在 `static` 后面的 `<T>` 表示“这个方法有自己的类型参数”。

读法是：这个方法接收一个 `T` 类型的参数，返回装着 `T` 的 `ApiResponse`。调用时不用显式写类型，编译器按参数推断：

```java
ApiResponse.ok(bookResponse)   → ApiResponse<BookResponse>
ApiResponse.ok(bookList)       → ApiResponse<List<BookResponse>>
```

### 为什么构造方法是 private

```java
private ApiResponse(int code, String msg, T data) {
```

`private` 表示只有这个类内部能调用它，外部无法 `new ApiResponse<>(...)`。

这样做是为了强制所有人走静态工厂方法。好处是成功码和成功文案只在 `ok()` 里写一次，不会出现“有人手工传了 code=0 但 msg 写成别的文字”这种不一致。

这也是第一次出现的写法：把构造方法关起来，只开放语义明确的入口。

### 三个字段为什么是 final

```java
private final int code;
```

`final` 表示这个字段只能在构造时赋值，之后不能再改。配合没有 setter，这个对象一旦创建就不会变。

不可变对象的好处是不用担心被别处偷偷修改，多线程环境下也更安全。响应模型只需要被读取，天然适合做成不可变的。

### fail 的三个重载

同名方法出现三次，参数不同，这叫方法重载。编译器按传入的参数决定调用哪一个：

| 写法 | 用途 |
| --- | --- |
| `fail(errorCode)` | 直接用枚举里的默认文案 |
| `fail(errorCode, msg)` | 需要更具体的说明，例如带上编号 |
| `fail(errorCode, msg, data)` | 失败时还要带回数据，例如字段错误明细 |

### 这个类的作用和调用关系

- 作用：定义统一的响应外壳，并提供构造它的标准入口。
- 编译期引用：`ApiResponseBodyAdvice`、`GlobalExceptionHandler`、`BookController` 的 delete 方法。
- 对象从哪来：由静态工厂方法创建，属于装数据的对象，不交给 Spring 管理。
- 运行期触发：Jackson 调用它的三个 getter 生成 JSON。
- 去掉会怎样：每个接口各自决定返回结构，调用方要写多套解析逻辑。

## 4. 创建 BusinessException

第 13 节的 `BookNotFoundException` 直接继承 `RuntimeException`，只带一句说明文字，没有返回码。现在需要让异常也能携带 `code`。

在 `exception` 包中新建 `BusinessException`：

```java
package com.example.bookapi.exception;

import com.example.bookapi.common.ErrorCode;

/**
 * 业务异常，携带业务返回码。
 */
public class BusinessException extends RuntimeException {

    private final ErrorCode errorCode;

    public BusinessException(ErrorCode errorCode) {
        super(errorCode.getMessage());
        this.errorCode = errorCode;
    }

    public BusinessException(ErrorCode errorCode, String message) {
        super(message);
        this.errorCode = errorCode;
    }

    public ErrorCode getErrorCode() {
        return errorCode;
    }
}
```

### 为什么要有这一层

有了它，处理器只需要认识一个类型就能处理所有业务错误：

```text
BusinessException                    ← 处理器只处理这一个类型
    ├─ BookNotFoundException
    ├─ 以后的库存不足异常
    └─ 以后的重复提交异常
```

以后新增业务错误时，只要继承 `BusinessException` 并给一个 `ErrorCode`，不需要改处理器。这是继承带来的实际好处：处理器面向父类型编程，子类型可以随意增加。

### 修改 BookNotFoundException

改成继承 `BusinessException`：

```java
package com.example.bookapi.exception;

import com.example.bookapi.common.ErrorCode;

public class BookNotFoundException extends BusinessException {

    public BookNotFoundException(Long id) {
        super(ErrorCode.BOOK_NOT_FOUND, "图书不存在，编号 " + id);
    }
}
```

`super(...)` 调用的是父类 `BusinessException` 的两参数构造方法，把返回码和带编号的说明文字一起交上去。

这个类现在只剩三行有效代码，作用是把“图书不存在”这件事和它的返回码、文案绑定在一起。`BookService` 里的代码一个字都不用改，因为类名和构造方法签名都没变。

### 继承关系带来的类型判断

现在这个异常同时属于三种类型：

```java
new BookNotFoundException(1L) instanceof BookNotFoundException  // true
new BookNotFoundException(1L) instanceof BusinessException      // true
new BookNotFoundException(1L) instanceof RuntimeException       // true
```

处理器声明处理 `BusinessException`，这个异常就能被接住。第 13 节讲过 `@ExceptionHandler` 写父类型会匹配子类型，这里正是利用了这一点。

## 5. 删除 ApiError

`ApiError` 的职责已经由 `ApiResponse` 承担，删掉它：

```text
src/main/java/com/example/bookapi/exception/ApiError.java
```

在 IDEA 里右键文件选择 **Delete**。如果提示有引用，说明处理器还没改完，先完成下一步。

## 6. 改写 GlobalExceptionHandler

完整代码：

```java
package com.example.bookapi.exception;

import com.example.bookapi.common.ApiResponse;
import com.example.bookapi.common.ErrorCode;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.http.converter.HttpMessageNotReadableException;
import org.springframework.validation.FieldError;
import org.springframework.web.bind.MethodArgumentNotValidException;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.RestControllerAdvice;
import org.springframework.web.method.annotation.MethodArgumentTypeMismatchException;

import java.util.LinkedHashMap;
import java.util.Map;

@RestControllerAdvice
public class GlobalExceptionHandler {

    private static final Logger log = LoggerFactory.getLogger(GlobalExceptionHandler.class);

    @ExceptionHandler(BusinessException.class)
    public ApiResponse<Void> handleBusinessException(BusinessException exception) {
        log.warn("业务异常，code={}，message={}", exception.getErrorCode().getCode(), exception.getMessage());
        return ApiResponse.fail(exception.getErrorCode(), exception.getMessage());
    }

    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ApiResponse<Map<String, String>> handleValidationError(MethodArgumentNotValidException exception) {
        Map<String, String> fieldErrors = new LinkedHashMap<String, String>();
        for (FieldError fieldError : exception.getBindingResult().getFieldErrors()) {
            fieldErrors.put(fieldError.getField(), fieldError.getDefaultMessage());
        }
        log.warn("参数校验失败，fieldErrors={}", fieldErrors);
        return ApiResponse.fail(ErrorCode.PARAM_INVALID, ErrorCode.PARAM_INVALID.getMessage(), fieldErrors);
    }

    @ExceptionHandler({HttpMessageNotReadableException.class, MethodArgumentTypeMismatchException.class})
    public ApiResponse<Void> handleUnreadableRequest(Exception exception) {
        log.warn("请求内容无法解析，{}", exception.getMessage());
        return ApiResponse.fail(ErrorCode.PARAM_INVALID);
    }

    @ExceptionHandler(Exception.class)
    public ApiResponse<Void> handleUnexpectedException(Exception exception) {
        log.error("未预期的异常", exception);
        return ApiResponse.fail(ErrorCode.SERVER_ERROR);
    }
}
```

### 四个方法的分工

| 方法 | 处理什么 | 返回码 |
| --- | --- | --- |
| `handleBusinessException` | 所有业务异常，包括图书不存在 | 异常自己携带的码 |
| `handleValidationError` | `@Valid` 校验失败 | 1001，`data` 里带字段明细 |
| `handleUnreadableRequest` | JSON 语法错误、路径参数类型不对 | 1001 |
| `handleUnexpectedException` | 其他任何异常 | 9999 |

和第 13 节相比多了两个方法。第 13 节那两种默认返回 Spring 内置结构的错误，现在也被接管了，所以响应结构真正做到了统一。

### @ResponseStatus 全部去掉了

第 13 节的处理器方法上有 `@ResponseStatus(HttpStatus.NOT_FOUND)` 这类注解。现在全部删除，方法不再指定状态码，HTTP 状态码就保持默认的 200。

这就是第 1 步选定的风格在代码上的体现：状态码固定，结果靠 `code` 表达。

### 兜底处理器为什么放在最后

```java
@ExceptionHandler(Exception.class)
```

`Exception` 是几乎所有异常的父类型，写上它意味着“剩下的都归我”。

匹配规则不看代码顺序，Spring 会选择继承关系上最接近的那个处理器。抛出 `BookNotFoundException` 时，`BusinessException` 比 `Exception` 更接近，所以走前者。方法写在文件哪个位置不影响结果，但按从具体到笼统的顺序排列更容易读。

有了这个兜底方法，任何漏掉的异常都会变成 9999，不会再出现第 13 节那种由内置 `/error` 接口返回的响应结构。

### 日志级别为什么不同

```java
log.warn(...)   业务异常、参数错误
log.error(...)  未预期的异常
```

业务异常属于正常的失败分支，例如用户查了一个不存在的编号，这不是程序缺陷，用 `warn` 记录足够。

未预期的异常说明代码有问题，需要人去看，用 `error` 并且把整个异常对象传进去，日志里才会打印完整堆栈。

注意最后一个方法的写法：

```java
log.error("未预期的异常", exception);
```

把异常对象作为最后一个参数传入，日志框架会输出堆栈。写成 `log.error("未预期的异常：" + exception.getMessage())` 就只有一行文字，排查时看不到出错位置。

### 两个 Logger 相关的写法

```java
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

private static final Logger log = LoggerFactory.getLogger(GlobalExceptionHandler.class);
```

SLF4J 是日志门面，`Logger` 是接口，具体实现由项目里的 Logback 提供。这套组合在第 1 节引入 `spring-boot-starter-web` 时就已经在依赖里了，不需要新增依赖。

`static final` 表示整个类共用一个日志对象，不会每次创建。参数传入当前类，日志里就会显示这个类名，方便定位来源。

`{}` 是占位符：

```java
log.warn("业务异常，code={}，message={}", code, message);
```

按顺序替换后面的参数。相比字符串拼接，只有这条日志真的要输出时才会拼接内容，级别关掉时几乎没有开销。

### 这个类的作用和调用关系

- 作用：把各种异常统一转换成 `ApiResponse`，并记录日志。
- 编译期引用：没有任何项目代码引用它。它引用 `ApiResponse`、`ErrorCode`、`BusinessException`。
- 对象从哪来：Spring 创建，`@RestControllerAdvice` 让它进入容器。
- 运行期触发：Controller 抛出异常时由 Spring 的异常处理流程回调，位置见本节第 14 步。
- 去掉会怎样：异常会回到 Spring 内置的处理逻辑，失败响应又变成几种不同结构。

## 7. 创建 ApiResponseBodyAdvice

现在成功响应还没有外壳。最直接的做法是每个 Controller 方法自己包一层：

```java
// 可行但重复
@GetMapping
public ApiResponse<List<BookResponse>> findAll() {
    return ApiResponse.ok(bookMapper.toResponseList(bookService.findAll()));
}
```

五个方法都要写一遍，以后每加一个接口都要记得写。漏写一个，那个接口的结构就和别人不一样。

更好的办法是让框架统一处理。在 `config` 包中新建 `ApiResponseBodyAdvice`：

```java
package com.example.bookapi.config;

import com.example.bookapi.common.ApiResponse;
import org.springframework.core.MethodParameter;
import org.springframework.http.MediaType;
import org.springframework.http.converter.HttpMessageConverter;
import org.springframework.http.server.ServerHttpRequest;
import org.springframework.http.server.ServerHttpResponse;
import org.springframework.web.bind.annotation.RestControllerAdvice;
import org.springframework.web.servlet.mvc.method.annotation.ResponseBodyAdvice;

/**
 * 把 controller 包下的接口返回值统一包装成 ApiResponse，
 * 这样每个 Controller 方法都不需要自己写包装代码。
 */
@RestControllerAdvice(basePackages = "com.example.bookapi.controller")
public class ApiResponseBodyAdvice implements ResponseBodyAdvice<Object> {

    @Override
    public boolean supports(MethodParameter returnType,
                            Class<? extends HttpMessageConverter<?>> converterType) {
        return !ApiResponse.class.isAssignableFrom(returnType.getParameterType());
    }

    @Override
    public Object beforeBodyWrite(Object body,
                                  MethodParameter returnType,
                                  MediaType selectedContentType,
                                  Class<? extends HttpMessageConverter<?>> selectedConverterType,
                                  ServerHttpRequest request,
                                  ServerHttpResponse response) {
        if (body instanceof ApiResponse) {
            return body;
        }
        return ApiResponse.ok(body);
    }
}
```

### ResponseBodyAdvice 是什么

它是 Spring MVC 提供的接口，作用是在“Controller 方法已经返回、Jackson 还没开始序列化”这个时机插一段自己的逻辑。

时间点很关键：

```text
Controller 方法 return 一个 BookResponse
      ↓
ResponseBodyAdvice.beforeBodyWrite 被回调        ← 在这里换成 ApiResponse
      ↓
Jackson 把返回的对象序列化成 JSON
      ↓
写入 HTTP 响应体
```

所以 Controller 方法可以继续返回 `BookResponse`，外壳由这一层补上。

### implements 和 @Override

```java
public class ApiResponseBodyAdvice implements ResponseBodyAdvice<Object> {
```

`implements` 表示这个类实现了某个接口，必须提供接口里声明的所有方法。第 12 节的 `DataInitializer implements CommandLineRunner` 是同一种写法。

```java
@Override
public boolean supports(...)
```

`@Override` 表示这个方法来自父类型。它不是必须写的，但强烈建议写：如果方法名或参数写错，编译器会立刻报错，而不是等到运行时发现方法没被调用。

两个方法的参数很长，在 IDEA 里不需要手打。类名后面写好 `implements ResponseBodyAdvice<Object>`，光标停在类名上按 `Option + Enter`，选择实现方法，IDEA 会自动生成完整签名。

### supports 决定要不要参与

```java
return !ApiResponse.class.isAssignableFrom(returnType.getParameterType());
```

这一行判断：方法的返回类型是不是已经是 `ApiResponse`。是的话返回 `false`，表示这次不用管。

`isAssignableFrom` 的读法是“左边这个类型能不能装下右边这个类型”。前面加 `!` 取反，意思就是“只有返回类型不是 ApiResponse 时才处理”。

需要这个判断，是因为 Controller 里的 delete 方法自己返回了 `ApiResponse`，不能再包一层变成两层外壳。

### beforeBodyWrite 做实际替换

```java
if (body instanceof ApiResponse) {
    return body;
}
return ApiResponse.ok(body);
```

`instanceof` 判断一个对象是不是某个类型。这里是第二道保险：即使 `supports` 判断漏了，已经是 `ApiResponse` 的响应体也不会被重复包装。

其余情况一律包成成功响应。返回 `null` 时会包成 `data` 为 `null` 的成功响应。

### basePackages 限定生效范围

```java
@RestControllerAdvice(basePackages = "com.example.bookapi.controller")
```

只对这个包下的 Controller 生效。

这一行不是可选优化，去掉会出问题。项目里还有一个第 3 节写的 `HelloController`，它在 `com.example.bookapi` 根包下，返回的是纯文本：

```java
return "Hello, Spring Boot!";
```

文本响应由专门处理字符串的转换器输出。如果这里把它包装成 `ApiResponse` 对象再交给那个转换器，类型对不上，请求会直接报错。

限定包名以后，`/hello` 保持原样，`/api/books` 走统一结构。真实项目里也常这样按包区分，例如面向 App 的接口统一包装，面向内部调用的接口保持原样。

### 这个类的作用和调用关系

- 作用：给指定包下的接口返回值自动加上统一外壳。
- 编译期引用：没有任何项目代码引用它。
- 对象从哪来：Spring 创建，`@RestControllerAdvice` 让它进入容器。
- 运行期触发：Spring MVC 在序列化响应体之前回调它的两个方法，每次请求都会经过。
- 去掉会怎样：`/api/books` 的成功响应退回到裸 JSON，失败响应仍然是统一结构，两者不一致。

## 8. 简化 BookController

现在 Controller 只需要去掉两个状态码注解，delete 方法返回统一结构：

```java
@GetMapping
public List<BookResponse> findAll() {
    return bookMapper.toResponseList(bookService.findAll());
}

@PostMapping
public BookResponse create(@Valid @RequestBody BookRequest request) {
    return bookMapper.toResponse(bookService.create(bookMapper.toEntity(request)));
}

@PutMapping("/{id}")
public BookResponse update(@PathVariable Long id, @Valid @RequestBody BookRequest request) {
    return bookMapper.toResponse(bookService.update(id, bookMapper.toEntity(request)));
}

@DeleteMapping("/{id}")
public ApiResponse<Void> delete(@PathVariable Long id) {
    bookService.delete(id);
    return ApiResponse.ok();
}

@GetMapping("/{id}")
public BookResponse findById(@PathVariable Long id) {
    return bookMapper.toResponse(bookService.findById(id));
}
```

同时删掉不再需要的两个 import：

```java
import org.springframework.http.HttpStatus;
import org.springframework.web.bind.annotation.ResponseStatus;
```

并新增一个：

```java
import com.example.bookapi.common.ApiResponse;
```

### 去掉 @ResponseStatus

第 13 节 POST 方法上有 `@ResponseStatus(HttpStatus.CREATED)`，delete 方法上有 `@ResponseStatus(HttpStatus.NO_CONTENT)`。两个都删掉，因为状态码统一为 200。

这是本节的第二处契约变化，第 12 步会集中列出。

### delete 为什么例外

其他四个方法都返回业务对象，交给 `ApiResponseBodyAdvice` 包装。delete 没有业务数据可返回，写法上有两种选择：

一种是保留 `void`，但 Spring 对返回 `void` 的方法不会走响应体序列化流程，包装逻辑不会被触发，客户端会收到 200 加空响应体，和其他接口不一致。

另一种是显式返回 `ApiResponse.ok()`，本节采用这种。`supports` 里那行判断正是为它准备的。

结论是：绝大多数方法交给统一包装，个别没有返回值的方法自己返回一次外壳。这类边界情况在真实项目里也存在，处理方式就是显式写清楚。

## 9. 更新 Controller 测试

`BookControllerTest` 的断言全部要改，因为字段位置变了。

类上的注解多导入一个类：

```java
@WebMvcTest(BookController.class)

```

原因和第 15 节一样：`@WebMvcTest` 只加载 Web 层组件。`ApiResponseBodyAdvice` 虽然带 `@RestControllerAdvice`，但它在 `config` 包下，属于需要显式导入的类型。不导入的话，测试里的响应不会被包装，断言 `$.code` 会失败。

| 断言的内容 | 第 15 节 | 本节 |
| --- | --- | --- |
| 成功状态 | `status().isCreated()` 等 | 一律 `status().isOk()` |
| 业务结果 | 看状态码 | `jsonPath("$.code")` |
| 单本图书的 id | `$.id` | `$.data.id` |
| 列表长度 | `$.length()` | `$.data.length()` |
| 列表第一项 | `$[0].title` | `$.data[0].title` |
| 字段错误 | `$.fieldErrors.title` | `$.data.title` |
| 错误说明 | `$.message` | `$.msg` |

## 11. 给 Service 测试补一条断言

`BookServiceTest` 里验证异常的那个用例，可以顺便确认返回码：

```java
@Test
void findByIdThrowsWhenIdDoesNotExist() {
    when(bookRepository.findById(99L)).thenReturn(Optional.empty());

    assertThatThrownBy(() -> bookService.findById(99L))
            .isInstanceOf(BookNotFoundException.class)
            .hasMessage("图书不存在，编号 99")
            .extracting(exception -> ((BookNotFoundException) exception).getErrorCode())
            .isEqualTo(ErrorCode.BOOK_NOT_FOUND);
}
```

`extracting` 的作用是从断言对象里取出一部分继续断言。这里取出异常携带的 `ErrorCode`，确认它是 1002 对应的那个枚举值。

括号里 `(BookNotFoundException) exception` 是强制类型转换，因为 `extracting` 拿到的是通用的 `Throwable` 类型，需要先转换成具体类型才能调用 `getErrorCode()`。

## 14. 完整调用链路

### 启动阶段新增了什么

```text
... 扫描 com.example.bookapi 及子包
      ↓
扫描到 GlobalExceptionHandler(@RestControllerAdvice)
   登记两类异常处理方法，本节增加到四类
      ↓
扫描到 ApiResponseBodyAdvice(@RestControllerAdvice)          ← 本节新增
   它实现了 ResponseBodyAdvice，被登记进响应处理链
   basePackages 限定它只对 controller 包生效
      ↓
JVM 首次用到 ErrorCode 时创建四个枚举实例，全程复用      ← 本节新增
      ↓
... 其余与上一节相同
```

`ApiResponse` 不是 Bean，每次响应都会新建一个，用完丢弃。

### 请求阶段：成功响应怎样被包装

以查询单本图书为例：

```text
curl 发出 GET /api/books/1
      ↓
Tomcat → DispatcherServlet 找到 BookController.findById
      ↓
Controller 调用 Service，拿到 Book 实体
      ↓
bookMapper.toResponse(book) 得到 BookResponse
      ↓
Controller 返回 BookResponse
      ↓
Spring 准备写响应体，先检查有没有 ResponseBodyAdvice
      ↓
ApiResponseBodyAdvice.supports 判断返回类型
   BookResponse 不是 ApiResponse → 返回 true，参与处理
      ↓
ApiResponseBodyAdvice.beforeBodyWrite
   body 不是 ApiResponse → 返回 ApiResponse.ok(body)
      ↓
Jackson 序列化 ApiResponse
   调用 getCode、getMsg、getData
   getData 返回 BookResponse，继续调用它的三个 getter
      ↓
{"code":0,"msg":"成功","data":{"id":1,...}}
      ↓
状态码保持 200，Tomcat 返回响应
```

关键点是最后的序列化：Jackson 遇到嵌套对象会继续往里序列化，所以外壳和数据是一次生成的。

### 请求阶段：失败响应怎样被包装

以查询不存在的编号为例：

```text
curl 发出 GET /api/books/99
      ↓
Controller 调用 bookService.findById(99L)
      ↓
Repository 查询数据库，返回空 Optional（控制台能看到 select）
      ↓
orElseThrow 抛出 BookNotFoundException
      ↓
异常穿过 Controller，被 DispatcherServlet 捕获
      ↓
ExceptionHandlerExceptionResolver 查登记表
   BookNotFoundException 的父类型 BusinessException 有处理方法
      ↓
GlobalExceptionHandler.handleBusinessException 被回调
   log.warn 记录一行日志
   返回 ApiResponse.fail(ErrorCode.BOOK_NOT_FOUND, "图书不存在，编号 99")
      ↓
方法返回类型已经是 ApiResponse
   ApiResponseBodyAdvice 不作用于 exception 包下的方法，不会重复包装
      ↓
Jackson 序列化
      ↓
{"code":1002,"msg":"图书不存在，编号 99","data":null}
      ↓
方法上没有 @ResponseStatus，状态码保持 200
```

和第 13 节相比，链路结构没变，变的只有两处：处理器认的是父类型 `BusinessException`，以及不再设置状态码。

### 四条失败路径现在都归自己管

```text
Controller 抛出异常
      ↓
1. ExceptionHandlerExceptionResolver 查登记表
   ├─ BusinessException            → code 用异常自带的
   ├─ MethodArgumentNotValidException → 1001，data 带字段明细
   ├─ HttpMessageNotReadableException → 1001
   ├─ MethodArgumentTypeMismatchException → 1001
   └─ Exception                    → 9999
      ↓
全部命中，不会再往下走
```

第 13 节这张图后面还有两级：Spring 内置处理器和 `/error` 兜底。现在因为有了 `Exception` 兜底方法，请求不会再走到那两级，响应结构因此完全可控。

需要留一个心眼：应用还没启动、端口不通、请求被网关拦下这些情况，客户端仍然会收到非 200 的响应，因为那时请求根本没进到我们的代码里。所以客户端代码要同时处理两种情况，先判断网络层是否成功，再判断 `code`。

### 本节新增类的引用与调用关系

| 类 | 谁引用它 | 运行期谁调用它 | 触发时机 |
| --- | --- | --- | --- |
| `ErrorCode` | `ApiResponse`、`BusinessException`、`GlobalExceptionHandler` | 上面这些类读取它的 getter | 构造响应和异常时 |
| `ApiResponse` | `ApiResponseBodyAdvice`、`GlobalExceptionHandler`、`BookController.delete` | 静态工厂方法被调用，Jackson 调用 getter | 每次响应 |
| `BusinessException` | `BookNotFoundException` 继承它，`GlobalExceptionHandler` 处理它 | 不需要被调用，只需要被抛出和被处理 | 业务失败时 |
| `ApiResponseBodyAdvice` | 没有任何项目代码引用 | Spring MVC 在写响应体之前回调 | 每次 controller 包下的请求 |

`ApiResponseBodyAdvice` 是本课程第三种框架回调写法。三种放在一起对比：

| 写法 | 例子 | 回调时机 |
| --- | --- | --- |
| 实现 `CommandLineRunner` | `DataInitializer` | 启动完成后一次 |
| `@ExceptionHandler` 方法 | `GlobalExceptionHandler` | 出现对应异常时 |
| 实现 `ResponseBodyAdvice` | `ApiResponseBodyAdvice` | 每次写响应体之前 |

共同点是：项目里没有代码调用它们，都靠实现特定接口或标注特定注解被框架发现。判断这类代码是否生效，要看它有没有被扫描到、限定条件是否匹配，而不是搜索调用处。

## 15. 本节推进了哪项生产标准

| 项目 | 本节之前 | 本节之后 |
| --- | --- | --- |
| 错误契约 | 成功和失败结构不同，失败还有三种格式 | 全部接口同一结构，失败原因由 `code` 表达 |
| 可观测 | 异常只有 Spring 内置日志 | 每类异常都有自己的日志，业务失败用 warn，未预期用 error 带堆栈 |
| 测试 | 21 个用例 | 27 个用例，返回码和文案被锁定 |

仍然欠缺的部分：

- 返回码只有四个，真实项目会按模块分段并配套文档。
- 错误文案只有中文，多语言场景需要按请求头返回对应语言。
- 日志里还没有可以串联一次请求的标识，出问题时无法把多条日志关联起来。
- 接口没有版本号，本节这种结构调整只能靠直接替换。
- 状态码固定 200 之后，需要在监控侧按 `code` 统计失败率，否则错误在监控上看不见。

## 常见问题

### 响应里出现两层 code

说明返回值被包装了两次。检查 `supports` 方法是否写了 `!` 取反，以及 `beforeBodyWrite` 里是否有 `instanceof ApiResponse` 的判断。

### 成功响应没有外壳，失败响应有

`ApiResponseBodyAdvice` 没有生效。检查三点：类上有 `@RestControllerAdvice`，`basePackages` 与 Controller 实际所在的包一致，类在能被扫描到的包下。

### 访问 /hello 报错

`basePackages` 写得太宽，把返回纯文本的 Controller 也包含进来了。限定到 `com.example.bookapi.controller` 即可。

### 删除接口返回空响应体

delete 方法可能还是 `void`。返回 `void` 时不会触发响应体包装，改成返回 `ApiResponse.ok()`。

### 编译报找不到 ApiError

`ApiError` 已经删除。检查是否还有文件引用它，通常是 `GlobalExceptionHandler` 没有改完。

### 测试断言 $.code 失败，实际取到 null

测试类上没有导入包装器。补成：

```java
@Import({BookMapper.class, ApiResponseBodyAdvice.class})
```

### 编号不存在时返回 9999 而不是 1002

说明异常没有被业务异常处理方法接住，而是落到了兜底方法。确认 `BookNotFoundException` 继承的是 `BusinessException`，并且处理器里声明的是 `BusinessException.class`。

### 想临时看真实的 HTTP 状态码

统一结构之后状态码不再表达业务结果。排查问题时可以看控制台日志，业务失败会有 `warn` 一行，未预期异常会有 `error` 和完整堆栈。
